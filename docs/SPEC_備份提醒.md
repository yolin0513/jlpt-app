# SPEC_備份提醒 — 太久沒匯出學習資料時，首頁提醒一次；順便向瀏覽器要「不要自動清資料」

> 狀態：已執行（2026-09-21，v1.14.0）
> 規劃：Fable 5.1 統籌 Session，2026-09-21。**本檔取代草稿 `docs/SPEC_backup_reminder.md`**（請在那份檔頭加一行「已由 `SPEC_備份提醒.md` 取代」，內容不用改）。Yolin 2026-09-21 指示統籌者審草稿；這一份統籌者與 Dispatch 判斷可以直接做、不必先問他（保護的是無法重建的資料；唯一的使用感受參數附了建議值，他事後可以改）。事實依據：統籌者 2026-09-21 對 `36c9da6` 的唯讀實查（行號以你讀到的為準）。

## 一句話

學習進度只存在這一個瀏覽器裡，沒有任何別的副本。距離上次匯出超過 14 天、而且這段期間有新的學習紀錄 → 首頁出現一張提醒卡，一鍵匯出；可以「這週先不要」，不能永久關掉。另外在使用者按匯出時，順便向瀏覽器請求持久儲存，統計頁用一行字照實顯示結果。

## 1. 現況（勘查事實）

- 五個 store：`progress`、`mistakes`、`daily`、`meta`（`{k, v}`）、`favorites`。沒有後端。
- 匯出：統計頁的按鈕「⬇️ 匯出學習資料（JSON）」→ `stats.js` 的 `doExport` → `store.exportAll()`（`EXPORT_VERSION = 3`，連 `meta` 一起匯出）。匯入是「取代」（先清空再寫入，`meta` 也會被備份裡的蓋掉）。`resetAll` 不清 `meta`。
- App 從來沒有記「上次什麼時候匯出」，也沒有呼叫過 `navigator.storage.persist()`。
- 你的 STATUS §3.3：新設定或小型紀錄放進既有的 `meta` store **不算異動較大**（先例：`examHistory`）。這一份只新增 `meta` 的 key，不動 IndexedDB schema、不動備份格式版本、不動 Service Worker 的快取策略 → **不用投票**。
- 測試全部是 puppeteer 端對端（`audit.mjs` 等三支，150 項，222 秒，每版全跑）；沒有單元測試層、沒有突變套件。

## 2. 目標與非目標

**目標**：G1 使用者太久沒備份、而且有東西可丟時，看得到提醒、一鍵就能備份；G2 剛備份過、或根本沒有新進度時，不打擾；G3 不騙人——「持久儲存」只講瀏覽器答應了什麼，不講成「資料安全了」。

**非目標**：不做雲端同步、不做自動備份、不動備份格式（`EXPORT_VERSION` 維持 3）、不動匯入的語意、不新增設定頁的開關、不做推播或系統通知（那是 `SPEC_feature_candidates` 的事，未決）。

## 3. 規則

- **R1 記錄上次匯出**：`doExport` 成功產生檔案之後（`exportAll` 沒丟錯、下載已觸發），寫 `meta`：`lastExportAt`（ISO 字串）。失敗不寫。**寫入的時機在 `exportAll()` 取完資料之後**——這樣備份檔裡帶的是「上一次」的值，不會自己記到自己；理由見 R5。
- **R2 什麼時候提醒**（兩個條件都成立）：
  1. 距 `lastExportAt` 超過 `BACKUP_REMIND_DAYS = 14` 天；**從沒匯出過**的，改看「有學習紀錄的日子 ≥ 3 天」（剛裝好、還沒東西可丟的人不提醒）。
  2. `lastExportAt` 之後有新的學習紀錄（`daily` 裡有晚於那一天、而且真的有作答的日子）。沒有新進度就沒有東西會丟，不提醒。
  `14`、`3` 各做成具名常數並寫註解。14 是統籌者的建議值，Yolin 可以改。
- **R3 提醒長什麼樣**：首頁一張卡（樣式沿用既有的提示卡，不新增視覺元素種類），內容：上次匯出是幾天前（或「還沒有匯出過」）＋這段期間學了幾天；一顆主要按鈕「現在匯出」（走同一支 `doExport`，不要另寫一份匯出）；一顆次要按鈕「這週先不要」。文字要誠實：說的是「學習進度只存在這台裝置的這個瀏覽器裡」，不要寫成恐嚇，也不要寫「建議」以外的保證。措辭你定，寫進回報。
- **R4 這週先不要**：寫 `meta`：`backupSnoozeUntil`＝現在＋7 天；到期前不顯示。**沒有永久關閉**（資料丟了救不回來，這個提醒的成本只是一張卡）。匯出成功 → 清掉 snooze。
- **R5 匯入之後**：匯入是取代，`meta` 會被備份裡的值蓋掉。匯入成功後把 `lastExportAt` 設成**那份備份的 `exportedAt`**（資料此刻跟那份備份一樣安全）、清掉 `backupSnoozeUntil`。舊備份沒有 `exportedAt` → 不設（當成沒匯出過，照 R2 的規則走）。
- **R6 持久儲存**：
  - 只在**使用者按了匯出**（統計頁的按鈕或提醒卡的按鈕）時呼叫 `navigator.storage.persist()`——要有使用者手勢；**不要在啟動時呼叫**（有的瀏覽器會跳權限詢問，使用者一開 App 就被問會嚇到）。不支援這個 API 的瀏覽器直接略過，不報錯。
  - 統計頁「資料管理」那一區加一行小字，用 `navigator.storage.persisted()` 的結果照實寫：答應了 →「這個瀏覽器已答應不會自動清掉這裡的資料（手動清除瀏覽資料或移除 App 仍然會清掉）」；沒答應或不支援 →「這個瀏覽器可能在空間不足時清掉這裡的資料，請定期匯出」。措辭你定，但括號裡那個但書的意思要在。
- **R7 多裝置**：每一台裝置、每一個瀏覽器各有各的資料與各自的 `lastExportAt`，這是現狀，不處理；提醒卡的文字裡「這台裝置的這個瀏覽器」就是在講這件事。

## 4. 與現有規則的交互

| 現有的東西 | 會不會衝突 | 結論 |
|---|---|---|
| 備份格式 v3、`idScheme` | `meta` 多兩個 key，會跟著匯出 | 無害；`inspectBackup` 不用改。舊版 App 匯入新備份：多的 `meta` key 它不認得也不會壞（請實查確認）|
| `resetAll` 不清 `meta` | 重置後 `lastExportAt` 還在、但學習紀錄清空了 | R2 第 2 個條件自然不成立 → 不提醒。補一條斷言 |
| 首頁既有的卡片順序 | 新卡放哪 | 放在不擋「開始學習」主要動線的位置；你定，附截圖說明 |
| Service Worker | 新增／修改 `js/` 檔 | 照你現行的發版流程升版；不改快取策略 |
| iOS 主畫面 App | 下載 JSON 在 standalone 模式可能存不下來（StockDiary 有同類的未解問題）| **這一份不解決它**。但請實查你現有的 `doExport` 在這種情況下會不會丟錯：如果匯出其實沒成功卻寫了 `lastExportAt`，提醒就會被錯誤地消掉——這是 R1「成功才寫」要守的。無法在 headless 環境確認的部分，照實寫「未確認」，列進待 Yolin 真機確認的清單 |
