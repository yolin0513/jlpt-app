# SPEC：讀解題庫（草稿）

- **狀態**：規劃中，尚未動工。
- **背景**：v1.11.0 的模擬考只有「文字・語彙／文法／聽解」三科，**沒有讀解**。
  UI 上已明講「本 App 沒有讀解題庫，模擬考不含讀解，分數不等同真實考試總分」——這是刻意的誠實聲明，不是遺漏。
- **優先度建議**：中。補上後模擬考才接近真實考試結構，但工作量與資料風險都比前幾輪大。

## 為什麼還沒做

1. **內容必須自己寫**：不能搬 JLPT 官方或市售題本的文章（著作權）。每篇短文＋設問都要原創、標假名、附中譯。
2. **需要新的資料型別**：現有 `data/src/*.txt` 是一行一條的 pipe 格式，放不下「一篇文章＋多道設問」。
   得新增來源格式、改 `build_data.py`、manifest 多一個區塊 → 依本專案規則屬**「異動較大」（資料結構／JSON schema 變更）**，
   動工前要先走多代理投票。
3. **不能影響既有 id 與進度**：讀解題要有自己的 id 命名空間（例如 `n3-r-0001`），不可混進 vocab／grammar 的行序編號。

## 真實 JLPT 讀解的題型（動工前要再查證最新出題基準）

- 各級共通：短文（内容理解・短文）、中文（内容理解・中文）、情報検索（從廣告、公告等找資訊）。
- N2／N1 另有：長文、統合理解（比較兩篇文章）、主張理解。
- 真實考試的讀解與文法同屬「言語知識（文法）・讀解」科，合格判定要一起算；
  **`js/views/exam.js` 的科目結構與 `PASS_SECTION`／`PASS_TOTAL` 換算要跟著重新檢查**（目前的換算是在「沒有讀解」的前提下訂的）。

## 草案

- 每級先做少量（例如 10 篇短文、每篇 1–3 題），驗證出題與作答流程後再擴充
- 題型先做「短文理解」，中長文與資訊檢索之後再說
- 模擬考加入讀解科時，時間仍照「真實考試總時間 ÷ 題數」換算；合格判定要把讀解併入「言語知識・讀解」科
