## §5 測試紀律

1. **每條新斷言都要證明它會紅**：把對應邏輯改壞（突變），或拿修正前的程式跑，測試必須失敗；修回去必須綠。修 bug 時補一條「修正前會紅」的回歸斷言，並說明既有測試為什麼沒抓到。有新行為就補斷言。
2. **不寫假斷言。** 抓到過的形狀：母體是空的；母體恰好是「有問題的那幾個」；等待條件在上一頁就已經成立；反例太弱、被別條規則順便擋掉；掃描器把註解當程式碼；「應該是 0」旁邊沒有「母體非空」。寫完一條 `noneOf`／`everyOf` 就問一次：**這個母體現在有幾個元素？** 註解不是斷言。
3. **檢查器要有對照組**：餵已知該被抓到的輸入，斷言真的抓到。**斷言驗語意、不貼字面。** 對照組**一定要有**自己造的合成樣本，而且跑的是同一個檢查（同一個搜尋式、同一段程式）；真實資料可以當第二道對照，不能單獨當對照組——它會隨時間變（實例：公開前自查的 email 對照組用 git 歷史的作者信箱，改用 noreply 之後就被排除規則濾掉、命中 0）。
4. **從使用者實際會走的入口測**：每個功能至少一條斷言從真實入口（畫面上的按鈕、對外的函式）進去，不能只驗內層純函式。
5. **含 regex 或反斜線的測試碼、補丁，一律用 Write／Edit 工具直接寫檔，不要經過 shell heredoc 或 `node -e`**：`\s` 變 `\\s` 或被吃掉都不報錯、測試照樣綠、但永遠不命中。
6. **打真網路的測試不進 `npm test`**，另開獨立指令；對外部服務的請求頻率照該服務的規矩。
7. **不必每一版都跑全套測試：平常跑受影響的就夠，全面檢測由 Yolin 定期指定。**（Yolin 2026-09-12 對全部專案的指示；2026-09-19 重申：「不用每一次小改動都全測，我會定期進行全面檢測」）這一條是**解除義務，不是設上限**——想多跑、想跑全套，永遠可以，不需要誰同意；本 App 規定每版要跑哪些的，照本 App 的規定。怎麼判定「受影響」由各 App 自己定。沒有放寬的那一條：新斷言仍然必須證明會紅。
   **耗時很久的整套（突變整套、全面檢測）**：等一批交辦事項做完再一起跑、一起看（Yolin 2026-09-19），不必每版跑、也不照固定天數。由 Yolin 指定；Session 不必自己跑（想跑永遠可以）。各 App 在自己的 STATUS 寫明「整套」指什麼、實測要跑多久、以及上限（距上次整套幾版、幾條突變或新斷言從未整套跑過）——上限照本 App 整套的成本訂：要跑幾小時的訂緊一點；只要幾分鐘的可以訂得很寬，或乾脆寫「每版都跑整套、不需要上限」。耗時還沒量過就寫「待量」，不要猜；超過上限時，回報最前面用一行講出來並建議「這一批做完就跑」，沒超過不必每次提。**成本算對地方**：整套是機器在背景跑，花的是時間，不是 token；花 token 的是處理結果的來回——所以要省的是「處理的次數」，結果一次回報、依根因分組。回報寫明是在哪個 commit 上跑的；沒紅的先在最新版複驗再處理。**整套的證據要進 repo**（Yolin 2026-09-23）：每次跑完，把日期、commit、範圍、條數、結果、耗時、沒紅的清單寫進 STATUS 或一個進版控的摘要檔——只存在本機 log 等於沒有紀錄。**完整的 log 寫到 repo 底下、被 `.gitignore` 擋掉的目錄（例如 `.logs/`）**，檔名帶日期與 commit；不要寫在系統暫存目錄或 session 的暫存區——跑好幾個小時的整套，啟動它的 session 可能中途被關掉，暫存目錄會跟著消失。**刪一條突變之前，要能說出這段程式為什麼在任何真實路徑上都走不到**；說不出來，就是測試走錯路，要改的是測試。
8. 隨機或情境敏感的輸出（排程、排菜、抽樣）不得綁死單一結果。需要特定情境才分得出對錯的斷言：優先自己造情境、直接呼叫被測的函式；若用整段產生的結果，先寫一條前置斷言確認情境存在，不成立就紅。**固定 seed 不算釘住情境**（資料或規則一改，同一個 seed 的結果就變）；沒有前置的「至少 1 個」就是假斷言。前置斷言自己也要用突變證明會紅（把情境拿掉，它必須紅）。統計型斷言另照各 App 的做法（多組種子量餘裕）。沒有單元測試層、只有端對端測試的 App，「自己造情境」就用它造得出來的方式（預置儲存狀態、URL 參數）；前置斷言照樣要。
9. **突變的 `expect`**（有這個機制的 App）：`expect` 是用來確認「紅的是指定的那一條」，所以**不要寫會變動的數字或整句訊息**——斷言訊息一改，突變就變成「紅錯地方」。訊息本身沒有穩定的開頭時，不要把 `expect` 寫鬆，而是**在訊息前面加一個固定標籤當錨點**（例：訊息寫成「早餐道數門檻：早餐 N 道…」，`expect` 比「早餐道數門檻：」）。改任何斷言的訊息時，一起搜突變清單裡含舊文字的 `expect`。秒級的突變檢查要同時查「`expect` 在對應測試的原始碼裡找得到」，不必等整套才發現過期；還沒有這個檢查的，列進本 App 的待辦，下次動突變機制時補。
10. **加資料之前，先查畫面上依筆數寫死的上限**（例如選單只列前 N 筆）：新加的資料可能永遠排不進畫面，卻沒有任何測試會紅。有這種上限的，加完要有一條斷言從畫面數得到新資料。
