## 0. 本 App 的情況（跟 MealMate 不一樣的地方）

- **只有一支被測程式、一個驗法**：34 條突變全是 `scripts/test_pushsafe.sh` 裡 `case "$MUTATE"` 的分支，由同一支驗法驗（`TEST_PUSHSAFE_MUTATE=<名稱> bash scripts/test_pushsafe.sh`）。突變清單本身就在驗法檔裡（實測：34 種，與檔頭列的一致）。
- **突變只改暫存 clone**：驗法先 clone 到 `mktemp -d`、`cd` 進去才改檔（讀程式＋**實測**：2026-10-02 強制終止時主 repo 142 支檔位元組與 HEAD 一致）。所以樣板 §七「改壞主工作區之前先寫還原紀錄」那一套**本 App 不需要**——主工作區根本不寫。保留的是它的精神：開跑前主 repo 必須等於 HEAD、中斷要留得下痕跡（見 §4）。
- **單條很貴**：實測 176～254 秒（5 條，平均 227 秒），整套外推約 2.1 小時（只當上限參考）。
- **「紅在預期」現在沒有機器可讀的答案**：每條突變該紅哪幾個情境，只寫在證據檔的摘要裡（而且其中 29 條已降級為「曾有紀錄、無法複核」）。

## 1. 突變清單與「預期」

- 新增一張**預期表** `scripts/mutation-expect.tsv`（進版控）：每條突變一列——名稱、預期結果類別（`red`／`equivalent`）、預期紅的情境編號集合、理由說明。
  - **預期只用情境編號、集合全等比對，不用文字錨點**（2026-10-02 改，Dispatch 轉遊戲專案與 StockDiary 的發現：一段理由文字可能同時對應好幾個斷言，任何一個紅了都算抓到）。情境編號 sNN 每個只對應一個情境函式，lint 的情境母體檢查保證不重複——結構上沒有歧義。現況量測：34 條裡唯一對應 0、歧義 0、**判斷不了 34**（預期表還沒建，沒有機器讀得到的預期）。
  - **預期清單過期的前置檢查**（已寫進 `scripts/mkevidence_mut.py`）：預期表裡的每一條突變要在 `test_pushsafe.sh` 的 case 分支裡、每一個預期紅的情境要在 `LIST` 裡；不存在就行首「MKEVIDENCE STALE-EXPECT:」、回 3、逐項點名、不寫檔，跟「不如預期」分開。突變名稱以 case 分支為準，並跟檔頭列的清單互相核對。
  - **判對時也印出實際紅在哪**：閘門驗法本來就每個情境都印一行 yes／no（判對、判錯都印），證據檔每一條都寫實際紅的情境集合——不只在不符時才看得到。
  - `nocheck` 記 `equivalent`（已知的等價突變，理由見證據檔）。
  - `oldparse`、`oldparse+nocheck` 預期是「lint 第一關擋下」，照實記這一點（它們驗的是 lint 抓得到舊抽法，不是自查本身）。
- **孤兒檢查兩邊都報**：驗法裡有、預期表沒有；預期表有、驗法裡已經沒有。用登記制（只認表上的）。
- 預期表的第一版：**照 2026-10-02 起重跑出來的結果填**，不從證據檔的舊摘要抄（舊摘要分不出情境成立與否）。

## 2. 執行器 `scripts/mutate_pushsafe.py`（新）

- 一次一條、單線（§5.19）；每一條都用 `reslog.py` 包住，預估取帳本裡該條上次的實測秒數，沒有就寫 `unknown`。
- **單條逾時**：上次實測 ×3、至少 600 秒；逾時就 `taskkill /T /F` 整棵殺掉，記成「沒有結果（逾時被殺）」、接著跑下一條。
- **三種結果分開判**（樣板「情境未成立」一節），只看驗法自己印的痕跡：
  - **情境成立且紅在預期**：有「MUTATION ACTIVE」、回傳 1、紅的情境集合＝預期集合、每一個紅的擋下理由都對（沒有「擋下理由不對」）。等價突變：有「MUTATION ACTIVE」、回傳 0、「全部符合，但這一輪是突變」。
  - **紅錯地方**：情境成立（有「MUTATION ACTIVE」、回傳 1），但紅的集合不等於預期，或有「擋下理由不對」。算數、記成紅錯地方，**要人看**（對照組不夠精準或預期表過期）。
  - **情境未成立**：回傳 2（「ABORT … 造情境失敗」）、沒有「MUTATION ACTIVE」、逾時被殺、輸出沒有結尾那一行。**不算紅、不算通過、不算數**；換一次新的開跑重試，最多 3 次；都沒成立就印行首「⊘ 情境未成立」、執行器回傳專屬的值（4）。
  - 成立與未成立**分開數**（「34 條：成立 32、未成立 2（不算）；成立的裡面紅在預期 31、紅錯地方 1」），不寫「34 條都紅」。
- **每一條的完整輸出寫進 `.logs/mut-<日期時間>-<名稱>-<第幾次>.log`**（Dispatch 2026-10-02：證據不留暫存區）；帳本裡記 log 的檔名。
- **收尾**：突變跑完，驗法會刪掉主 repo 的驗法登記（推送閘因此會擋）——執行器最後要提醒「推送前先正常跑一次 `bash scripts/test_pushsafe.sh`」，不要自己偷偷登記。

## 3. 依賴範圍（從寬）——**這裡要 Dispatch 決定**

每條突變的結果由三樣決定：突變本身（驗法檔裡那一個分支的文字＋預期表那一列）、被測的那些檔、執行器。照樣板算三個雜湊，三個都沒變才沿用。問題在「被測的那些檔」：

- 驗法會 clone **整個 repo**，每個情境都跑完整的推送閘：lint 掃 `scripts/`、`js/`、`sw.js` 底下 54 支登記的腳本並做孤兒檢查（讀 `git ls-files` 與 `.gitignore`）；自查的真實檔對照組會讀 HEAD 裡「這次有新增行的那一類」的真實檔；F9 那幾個情境動到 `scripts/build_data.py`（推論）。
- 情境自己造的 commit 只動根目錄的合成 `.txt` 與 `scripts/build_data.py`（推論，讀程式）。
- 照樣板第 3、4、5 點「判斷不出就整個 repo、未知類別算進每一條」，**誠實的答案是：34 條的範圍都是整個 repo**（帳本與 `.logs/` 除外）。結果：任何一個檔改了（包括只改 `docs/STATUS.md`），34 條全部要重跑＝約 2 小時。

選項：

| | 做法 | 代價 |
|---|---|---|
| A | **接受整個 repo**。範圍化只帶來「沒改任何東西就沿用」與「中斷後續跑」 | 每次改任何檔都是 2 小時的重負載；實際上會變成「不跑」 |
| B | **用結構保證把 `docs/` 與 `data/` 排除**：驗法在 clone 裡、開始跑情境之前，把 `docs/` 與 `data/` 刪掉並 commit（複本裡），這樣任何情境都讀不到它們——跟 MealMate「伺服器一律不送 `docs/`」同一種保證；再加一個情境驗「複本裡真的沒有 `docs/`」。範圍＝其餘的檔 | 要改驗法本身（重跑閘門驗法＋這一輪 34 條才算數）；`docs/`、`data/` 以外的檔改了仍是全跑 |
| C | B ＋**按目標檔分組**：只改 lint 的突變 vs 只改自查的突變 vs 只改 `pushsafe.sh` 的……但每個情境都會跑到每一支閘門檔，**照從寬原則分不開**——不建議 | 規則變成「人工宣告只讀哪些」，樣板明講只准讓範圍變大，不准這樣縮 |

**建議 B**：本 App 最常改的是 `docs/`（STATUS、證據檔）與 `data/`（題庫），把這兩類排除才讓範圍化有意義；排除靠結構保證（複本裡刪掉），不靠宣告。B 做之前要先實測一次「刪掉 `docs/`、`data/` 之後 33 個情境照樣全符合」。

## 4. 帳本 `scripts/mutation-ledger.json`（進版控）

照樣板 §三，本 App 的差異：

- 每條：`last`（日期、commit、跑法、結果類別：`red-expected`／`red-wrong`／`equivalent`／`not-established`／`timeout`、算不算數、秒數、三個雜湊、log 檔名）、`lastFull`（最近一次算數的整套或補跑）。
- **沒有結果就是沒跑過**：`not-established`、`timeout` 一律 `counted: false`、不寫 `lastFull`；選擇邏輯把它們當成沒跑過，下一次一定挑進來。
  **對照組**（Dispatch 2026-10-02）：手動把一條改成 `timeout`，`--dry-run` 必須把它挑進來、理由寫「上次沒有結果」；把選擇邏輯改成忽略這個狀態的突變必須讓這個對照組紅。
- **中斷的兩處紀錄**：開跑每一條之前，帳本先寫 `inflight: {runSeq, 名稱, 開跑時間}` 並存檔，跑完清掉並寫結果。下次啟動：
  - `inflight` 還在＝上一次在那一條中途被殺：清掉 `.logs` 以外它留下的暫存目錄（照 `test_pushsafe_kill.py` 的認法），那一條記成 `not-established`（不是通過），再開始。
  - 主 repo 不等於 HEAD → 拒絕開跑，列出檔案（主工作區照理不會被寫，不等就表示有別的事發生）。
  - 本 App 不寫主工作區，所以沒有「還原紀錄被刪、壞檔被當原檔」的風險；兩處一致的檢查簡化為「帳本的 `inflight` 與磁碟上留下的暫存目錄」對得上（`inflight` 在、目錄不在：照常繼續並註明；目錄在、`inflight` 不在：列出、不刪，可能是別的程式的）。
- 寫檔用「寫暫存檔再 rename」。
- **初版**：34 條全部記「從沒在帳本裡跑過」，不從證據檔轉入（舊摘要分不出情境成立與否）。2026-10-02 重跑的 5 條有 `.logs/` 的 log，可以照實轉入，`lastFull` 不寫（那次不是用執行器跑的、沒有雜湊）。

## 5. 指令

| 指令 | 做什麼 |
|---|---|
| `python scripts/mutate_pushsafe.py --dry-run` | 只列：每一條會不會跑、理由；範圍種類；預估總秒數與歸類（§5.19 按次） |
| `python scripts/mutate_pushsafe.py` | 預設＝受影響的（雜湊變了、上次沒有結果、從沒跑過） |
| `--full` | 整套；這個 commit 上已算數跑過、雜湊沒變的跳過（中斷後同一個指令就是續跑） |
| `--only <名稱>` | 新防線當場證明會紅（§5.18 第 5 點） |
| `--limit N` | 這一次最多跑 N 條（分段） |

**開跑前的預估與歸類**（§5.19 按次）：選到的每一條取上次實測秒數加總；沒量過的那幾條讓整次歸重負載；超過 1 分鐘就要 Dispatch 許可（閘門突變單條約 4 分鐘，所以**任何一次執行器實跑都是重負載**，`--dry-run` 除外）。預估與實際一起寫進 `reslog-index.tsv`；連續 3 次實際超過預估 50%、或有一次越界沒拿許可，就要改預測法。**預測器的對照組**：餵一組事先寫好耗時的選擇，預測必須越過界線；把某一條的耗時改成 0 的突變必須讓它紅。

## 6. 驗法（全部在暫存目錄、不碰主工作區）

照樣板 §五：

- 範圍與雜湊的純函式：合成的 repo（記憶體裡的 `{路徑: 內容}`），每條規則一個樣本、答案事先寫好；反方向也要（改了範圍外的檔，雜湊不變——B 選項下就是改 `docs/` 的檔）。
- 結果分類器：餵事先寫好的驗法輸出（成立且紅在預期／紅錯地方／等價／回傳 2／沒有 MUTATION ACTIVE／沒有結尾），答案事先寫好；突變「把未成立判成紅」「把紅錯地方判成紅在預期」各一，必須紅。
- 真實入口：把一條突變換成一定很快結束的假突變（在暫存 repo 裡），連跑執行器：第一次要跑 → 沒改東西時沿用 → 改了範圍內的檔要跑 → （B）只改 `docs/` 沿用；一條假突變故意卡住、時限調短：記成 `timeout`、不算數，下一次 `--dry-run` 挑進來。
- 強制終止：執行器跑到一半 `taskkill /T /F`，下一次啟動要認出 `inflight`、清掉留下的暫存目錄、那一條記 `not-established`。

## 7. 要 Dispatch 決定的

1. 依賴範圍選 A、B 還是 C（建議 B）。
2. B 的話，驗法要改（複本裡刪 `docs/`、`data/`），改完要先跑一次閘門驗法確認 33 個情境照樣全符合（約 6 分鐘，常規）。
3. 實作排在第 2 場（29 條重跑）之前還是之後。**建議之後**：29 條先用現在的驗法單純重跑、log 進 `.logs/`、照第 2 節的三類分開判（我手動判、寫進 STATUS），它的結果就是預期表的第一版；執行器再照那份預期表做。
