## 為什麼改版

四個 App 做 v3 更新時回報的問題，統籌者彙整後改了四處（主檔 v3 → v4）。**沒有新政策**，都是把話講清楚：

1. **§0.2 回執範例**：v3 升版時統籌者漏改範例，它還寫著 v2；TripQuest、StockDiary、JLPT_App 各自抓到，而且都沒有自己動手改副本——這正是 §7 要的。新版把範例改成不含版本的寫法，以後升版不會再漏。
2. **§5.3 對照組用合成樣本**：StockDiary 發現，公開前自查的 email 類拿 git 歷史的作者信箱當對照組，改用 noreply 之後就被排除規則濾掉、命中 0。
3. **§5.7 整套的成本差很多**：MealMate 4.1 小時、StockDiary 約 3.5–4 小時（未實測）、JLPT_App 222 秒、TripQuest 沒量過。v3 是照最貴的那個寫的。新版要各 App 寫明「整套」指什麼、實測多久，上限照成本訂；幾分鐘就跑完的可以寫「每版都跑、不需要上限」；沒量過寫「待量」。
4. **§5.8 替只有端對端測試的 App 留口**（JLPT_App 提出）：造情境用它造得出來的方式（預置儲存狀態、URL 參數）；前置斷言照樣要。

# 四個 App 共用的工作慣例（CONVENTIONS.md）

適用：JLPT_App、StockDiary、TripQuest、MealMate。
主檔在統籌工作區（Fable 統籌 Session 的 repo）；每個 App 的 `docs/CONVENTIONS.md` 是內容相同的副本。**不要直接改副本**，要改照 §7。
這裡只收四個 App 都同意的規則。每個 App 自己的紅線、指令、門檻在它的 `CLAUDE.md` 與 `docs/STATUS.md`。

## §0 怎麼用這份

1. 開工前讀完本檔、本 App 的 `CLAUDE.md` 與 `docs/STATUS.md`。
2. 第一則回覆的第一行寫回執：`已讀共用慣例 vN（日期）`——N 與日期抄本檔第一行，不要抄這個範例。沒有回執，Yolin 就當你沒讀。

## §1 角色與流程（Yolin 2026-09-14 明訂）

1. **規劃：Fable 5.1（effort high）統籌 Session。** 理解需求、拆解、寫成規格。單一 App 的規格放該 App 的 `docs/SPEC_<主題>.md`；跨 App 的放統籌工作區。
2. **開發：Opus 5，平常 effort high；只有 Yolin 明講「大工程」才切 Max。** Opus 負責實作，也負責查找、蒐集資料。
3. **流程**：Fable 寫 spec → Opus 實作＋查資料 → 回報並逐項與 spec 對照 → 與 Yolin 確認。
4. **較大改動或值得討論的議題**：由 Fable 開 3 個代理投票，同一份 prompt、各自獨立、多數決、分歧採保守；各代理當統籌，查資料交給 Opus；Fable 彙整後回報。哪些算「較大」、實作途中臨時遇到時怎麼辦，看本 App 的規定。
5. **Fable 額度用盡就自動改用 Opus 5，不要停下來問。**（Yolin 2026-09-10 明訂）代理因 429／quota 失敗 → 改 `claude-opus-5` **整批重跑**（投票要在同一個模型上才可比）→ 回報註明「因 Fable 額度用盡改用 Opus 5」。連 Opus 5 也不可用才暫停。

## §2 授權的地板

1. **這三件一定先問 Yolin**：刪除或破壞使用者資料；花錢、或需要註冊帳號／綁卡的服務；動到本 App 以外的任何檔案。本 App 的投票或其他決策流程**不能取代**這一條：就算投票通過，只要做下去有刪除或破壞使用者資料的風險（例如改儲存格式、做資料遷移），動手前仍然先問。
2. **其他 App 的目錄可以讀、不可以寫**（讀來抄慣例、對照同一種 bug）。統籌 Session 只會在本 App 寫 `docs/SPEC_<主題>.md`；它不改程式、不 commit、不 push。

1. **禁止互動式提示框／多選題工具（`AskUserQuestion` 之類）。**（Yolin 2026-09-16 明訂）需要 Yolin 決定的事一律用**純文字**寫在回覆裡：列出選項、每個選項的代價、你的建議與理由，然後**停下來等**，由 Dispatch 轉達。理由：Yolin 常從手機或另一台電腦遠端操作，提示框只渲染在本機那台 PC，遠端點不到，Session 就此卡死。

## §4 給使用者看的文案要誠實

拿不到、算不出、還沒開放的，就照實寫（「尚未取得」「未估算」「這一版尚未開放」這類話）——不顯示 0、不用預設值冒充使用者輸入、不用舊資料冒充新資料。

## §5 測試紀律

1. **每條新斷言都要證明它會紅**：把對應邏輯改壞（突變），或拿修正前的程式跑，測試必須失敗；修回去必須綠。修 bug 時補一條「修正前會紅」的回歸斷言，並說明既有測試為什麼沒抓到。有新行為就補斷言。
2. **不寫假斷言。** 抓到過的形狀：母體是空的；母體恰好是「有問題的那幾個」；等待條件在上一頁就已經成立；反例太弱、被別條規則順便擋掉；掃描器把註解當程式碼；「應該是 0」旁邊沒有「母體非空」。寫完一條 `noneOf`／`everyOf` 就問一次：**這個母體現在有幾個元素？** 註解不是斷言。
3. **檢查器要有對照組**：餵已知該被抓到的輸入，斷言真的抓到。**斷言驗語意、不貼字面。** 對照組用自己造的合成樣本，不要借用會隨時間變的真實資料（實例：公開前自查的 email 對照組用 git 歷史的作者信箱，改用 noreply 之後就被排除規則濾掉、命中 0）。
4. **從使用者實際會走的入口測**：每個功能至少一條斷言從真實入口（畫面上的按鈕、對外的函式）進去，不能只驗內層純函式。
5. **含 regex 或反斜線的測試碼、補丁，一律用 Write／Edit 工具直接寫檔，不要經過 shell heredoc 或 `node -e`**：`\s` 變 `\\s` 或被吃掉都不報錯、測試照樣綠、但永遠不命中。
6. **打真網路的測試不進 `npm test`**，另開獨立指令；對外部服務的請求頻率照該服務的規矩。
7. **不必每一版都跑全套測試：平常跑受影響的就夠，全面檢測由 Yolin 定期指定。**（Yolin 2026-09-12 對全部專案的指示；2026-09-19 重申：「不用每一次小改動都全測，我會定期進行全面檢測」）這一條是**解除義務，不是設上限**——想多跑、想跑全套，永遠可以，不需要誰同意；本 App 規定每版要跑哪些的，照本 App 的規定。怎麼判定「受影響」由各 App 自己定。沒有放寬的那一條：新斷言仍然必須證明會紅。
   **耗時很久的整套（突變整套、全面檢測）**：等一批交辦事項做完再一起跑、一起看（Yolin 2026-09-19），不必每版跑、也不照固定天數。由 Yolin 指定；Session 不必自己跑（想跑永遠可以）。各 App 在自己的 STATUS 寫明「整套」指什麼、實測要跑多久、以及上限（距上次整套幾版、幾條突變或新斷言從未整套跑過）——上限照本 App 整套的成本訂：要跑幾小時的訂緊一點；只要幾分鐘的可以訂得很寬，或乾脆寫「每版都跑整套、不需要上限」。耗時還沒量過就寫「待量」，不要猜；超過上限時，回報最前面用一行講出來並建議「這一批做完就跑」，沒超過不必每次提。**成本算對地方**：整套是機器在背景跑，花的是時間，不是 token；花 token 的是處理結果的來回——所以要省的是「處理的次數」，結果一次回報、依根因分組。回報寫明是在哪個 commit 上跑的；沒紅的先在最新版複驗再處理。**刪一條突變之前，要能說出這段程式為什麼在任何真實路徑上都走不到**；說不出來，就是測試走錯路，要改的是測試。
8. 隨機或情境敏感的輸出（排程、排菜、抽樣）不得綁死單一結果。需要特定情境才分得出對錯的斷言：優先自己造情境、直接呼叫被測的函式；若用整段產生的結果，先寫一條前置斷言確認情境存在，不成立就紅。**固定 seed 不算釘住情境**（資料或規則一改，同一個 seed 的結果就變）；沒有前置的「至少 1 個」就是假斷言。前置斷言自己也要用突變證明會紅（把情境拿掉，它必須紅）。統計型斷言另照各 App 的做法（多組種子量餘裕）。沒有單元測試層、只有端對端測試的 App，「自己造情境」就用它造得出來的方式（預置儲存狀態、URL 參數）；前置斷言照樣要。
