## v11.1 的兩條修正（§5.19；MealMate 落實 v11 時撞出來，是條文本身寫糊了，不是執行者誤讀）

**一、合計上限只能由 Dispatch 執行。** 單一 Session 看不到別的專案開了幾個程序（MealMate 跑秒級語法檢查時，另一個專案的 4 個 node 一直開著，合計超過 4 個，它沒有辦法事先知道）。所以：
- **重負載開跑前向 Dispatch 要許可**（定義：會開 2 個以上工作程序，或預期超過 1 分鐘）。許可是一次一場，不累積。
- **秒級的單支檢查不需要許可**，照跑，但要記進資源紀錄。
- Session 自己的資源紀錄量的是**本 repo 的**程序數與記憶體，不要寫成「全機」——量不到的東西寫進紀錄，只會讓人填一個看起來合理的數字。Session 自己守的是本 repo 同時最多 4 個工作程序。

**二、常規測試套件不排隊，用實測時間分，不用套件名稱分。**
- **常規測試套件**（分鐘級）：不排隊，部署前必跑——本 App 規定的部署前測試是閘門，不是可選項。
- **突變整套／長跑**（十分鐘以上）：排隊，要許可。
- 界線用**實測時間**判定，不用估值——**沒量過就先量**（量的那一次當成重負載，要許可）。
- §0.3「不得放寬」連這兩條例外一起：不要把常規測試套件排進隊裡。

## v11.2 的兩條修正（TripQuest、JLPT 落實時撞出來）

**一、§5.19 歸類不能按指令名稱，要按次。** TripQuest 的 `test:affected` 是同一個指令，實測從 111 秒到 1109 秒（18.5 分）都有，取決於那次挑到 52 支裡的哪幾支——只要挑到 `layouttest`（單支 516～580 秒）就超過 10 分鐘。所以「這個指令屬常規／屬重負載」這個問法本身沒有答案。
- **歸類按次**：開跑前依這次的實際挑選範圍預測耗時，超過界線就要許可。不是按指令名稱登記一次。範圍裡有沒量過的、或預測不出來，就當重負載。
- **預測要被回頭檢查**：每次把「預估」與「實際」一起記進資源紀錄。只信預測而不回頭對，預測器壞掉時不會有任何東西紅——它只會一直預測「這次很短」。連續 3 次實際超過預估 50% 以上，或任何一次實際越過界線而那次沒拿許可，就要改預測法，改好之前一律當重負載。預測器本身要有對照組與突變。

**二、§5.20「對照組是合成字串」不算對照組。** JLPT 和 TripQuest 各自盤出同一種形狀：檢查分支的對照組只用合成字串餵進函式、不經讀檔——JLPT 專掃 `.js` 的 lint 分支從來沒有 `.js` 樣本，照樣印「掃了 53 支、0 命中」；TripQuest 的 `pipe` 有 `.mjs` 專用分支但樣本只有 `.sh`，跳脫掃描的 `.sh` 分支（`over-sh`）完全沒有樣本；`prepush-scan` 有 12 個分支從沒在真 commit 上驗過，只有 email 那一條走過真實的 git 抽取。
- **每一條檢查分支，對照組必須是它真正會掃的那一類真實檔／真實入口**，從命令列入口而不是直接呼叫內部函式；合成字串只證明規則語法沒寫錯，不證明它讀得到、掃得到。
- **造樣本的時候，先確認寫進檔裡的那一行真的含有違規字串**（TripQuest 把 `||` 拆成字串相接，寫進去的行其實不含 `|| true`，第一次因此沒紅）。

## v11.3 的一條補充（§5.20；JLPT 提出）

常設對照組每次推送都要跑，如果改成從命令列入口、就得暫時把樣本寫進真實的原始碼檔，有改壞原始碼的風險。解法是 JLPT 自查情境已在用的做法：
- **從命令列入口跑的對照組，在 repo 的暫存複本裡跑，不在工作區裡跑**（例：暫存目錄裡 clone 一份，做完整個刪掉）。這樣既走到真實的讀檔與入口路徑，也沒有改壞原始碼的風險。
- **跑完要比對工作區與 HEAD，確認沒有殘留**：跑之前、跑之後各取一次主工作區的狀態（`git status --porcelain` 與有改動的檔的雜湊），兩次必須相同；跑之前是乾淨的，跑之後就必須跟 HEAD 一樣乾淨。

## v11.4 的四條補充（§5.20 三條、§5.7 一條；前兩條是 v11.3 自己造出來的副作用，第三條是四家共同的發現）

**一、暫存複本必須含有這次要測的改動（§5.20）。** MealMate 照 v11.3 在暫存複本裡跑對照組，有一組 3 條沒抓到：`git clone` 拿到的是已 commit 的版本，突變改的是工作區，複本裡跑的一直是沒改壞的程式，輸出照樣顯示「跑完了」。
- clone 之後把工作區的相關目錄覆蓋過去，或用別的方式確保改動在複本裡。
- **要驗，不能只靠流程**：在複本裡把那支檔讀出來，確認改壞後的字串或違規樣本確實在裡面，確認到了才算情境成立；讀不到判「情境未成立」。
- 對照組沒抓到時，先查改動有沒有進到被測的那一份，再查規則本身。

**二、判斷結果類別不能用子字串比對（§5.20）。** MealMate 的執行器只看一行裡有沒有「✗」，把「✓」開頭、訊息提到 ✗ 的行算成紅；改成只認以 ✗ 開頭的行，8 條護欄突變的「抓到」作廢重驗。結果類別的判定要錨定在行首或固定欄位；說明文字裡提到那些符號不能影響判定。

**三、「情境未成立」是獨立的結果類別（§5.20）。** 紅錯地方＝情境成立、被別條規則擋下；情境未成立＝要測的狀況沒發生、什麼都沒量到。兩者意思相反。
- 不算紅、不算通過、不算數；帳本不記成跑過，下次選擇要再挑它；專屬的回傳值與行首標記。
- 判定依據取自情境自己留下的痕跡，不是執行器的推論（MealMate 的四個痕跡：壞檔還在、還原紀錄還在、被殺的探針只有「開始」沒有「結束」標記）。
- 沒成立就換新的暫存環境重試，有上限（例：3 次），到上限硬失敗，不得靜默補一次。
- 回報時成立與未成立分開數：「成立 6、未成立 2（不算）」，不准寫「8 條都紅」。
- 對照組：故意造一個必然不成立的情境，必須判成「情境未成立」，不能判成紅或綠。
- **逾時與崩潰歸進這一類，不得被回傳值吃掉**：StockDiary 的判定器對沒寫預期的突變只看結束碼，逾時被判成「✓ 變紅」；某支驗法逾時設 15 分鐘、實測約 55 分鐘，那兩條突變每次都逾時、每次都被記成被抓到，從來沒有證明過任何事。

**四、入庫的證據要能複核（§5.7）。** JLPT 有 29 條突變的證據只剩「紅 13、14」這種總數，原始 log 在 Session 暫存區、已經不在，只能降級成「曾有紀錄、無法複核」。
- 原始 log 寫進 `.logs/`（不留暫存區），不進版控（可能帶本機絕對路徑）。
- 入庫的證據檔由腳本從 log 產生、逐項：每一條一行，帶分類、預期紅哪幾條、實際紅哪幾條。
- 產生腳本入庫，做路徑與個資清洗，清洗配雙向對照組（含路徑的要被洗掉；分類資訊不能被一起洗光）。
- 母體檢查：證據檔行數等於這次跑的條數，不等就點名、非 0、不寫檔。
- 耗時數字進版控——否則換一台機器，按次預測永遠在冷啟動。

## v11.5 的補充（22 條，全部是四個專案 2026-10-02 下午實際跑下去撞出來的；條文與來源案例在附錄）

- **§5.23 環境與紀律（新）**：開跑前把 `bash` 等指令解成完整路徑，落在系統目錄或 WindowsApps 一律拒絕（WSL）；逐路徑 add、不用 `git add -A`；不因看起來不合理就丟實測值。

5. **推送的閘門：每一關都要真的擋得下。**（Yolin 2026-09-19 那句「只要不會有金鑰或個資上傳到公開就沒有問題」的執行方式）推送流程裡每一個「失敗就該停」的步驟，失敗時都必須回傳非 0，而且真的讓後面的步驟停下來：
   - **自查**：有命中、或任何一類的對照組沒命中，都回傳非 0，不推。
   - **推送本身**：失敗就停。不要接著做線上確認或整套檢查——那會對著沒推上去的舊版去驗，看起來還是綠的。
   - **推送後**：比對遠端的 HEAD 等於本機，才算推上去；這一道堵住「推了但沒成功」。

   **自查的範圍，是這次要推的每一個 commit 會公開的東西**：逐個 commit 的新增行（不要只比兩端——中間某個 commit 加了又刪掉的內容，照樣會被推上去；中途刪掉的檔也一樣）、commit 訊息、作者與提交者的名字與信箱。**範圍要照遠端的實際狀態算，不能照本機的追蹤分支算**：推送前先 `fetch`（或直接問遠端），讀不到遠端就停在自查那一關。原因：本機的追蹤分支可能跑在遠端前面——例如上一次「推送回報成功、遠端卻沒更新」之後（推送後那一關攔到的正是這種事），或遠端被倒退過；那時本機以為已經推上去的 commit，遠端其實沒有，照追蹤分支算，它們會落在範圍外，下一次推送就不經檢查被帶出去。**驗法要有一種情境專驗這點**：讓本機以為一個帶命中的 commit 已經在遠端、遠端其實沒有（例如先把它推上測試遠端、再把測試遠端的 main 退回舊值，或直接把本機的追蹤分支撥到它），再疊一個乾淨的 commit，閘門必須照樣擋下；把「取遠端實際狀態」那一步拿掉時，這一種必須報不符。**「我本來就有做」跟「有東西擋著它被改掉」是兩回事**：程式寫對了、註解也寫了理由，沒有這一種情境，下一個人把那一步拿掉，也不會有任何測試紅。同一個缺陷，換一個時序，結果可能從「擋下」變成「放行」，只看結果分不出來——這一次剛好擋下，不代表洞不在。

   **不要用管線包任何一步**（例如為了截短輸出加 `| tail -1`）：管線的回傳值是最後一個指令的，前面那一步的失敗會被吞掉，`&&` 照樣往下走，不報錯、沒有任何徵兆，只會在真的該擋的那一次默默放行。要看輸出就導到檔案再看，或在同一個 shell 先 `set -o pipefail`。

   **要用實際推送的那一整行實測，而且分別製造每一關的失敗**，不能只驗第一關：自查——餵一個一定會命中的合成樣本（放在自查會掃到的地方）；推送——讓推送失敗；推送後——讓遠端與本機對不上。製造失敗而不碰 GitHub 的做法：在暫存目錄建一個 bare repo 當測試遠端，放一個回傳 1 的 `pre-receive` hook 就是「推送被拒」，放一個把 main 退回舊值的 `post-receive` hook 就是「推送回報成功、遠端卻沒更新」。會擋的情境用 `--dry-run` 或這種本機測試遠端當保險，就算閘門沒擋住也只是試推、不會公開；用過真的遠端當測試，測試分支驗完就刪，再用 `git ls-remote` 確認遠端從來沒出現過它。每一關失敗用不同的回傳值（例如自查 1、推送 2、遠端與本機對不上 3），一看就知道是哪一關。

   **閘門腳本放在 repo 裡，不放 session 的暫存區。** session 會被刪、會撞額度、會被換掉；閘門跟著消失，就有一段沒有防線的空窗，新 session 重建時還可能重犯同樣的錯。**規則進 repo、資料不進 repo**：不能公開的內容（例如個資黑名單）從被 `.gitignore` 擋掉的檔案讀進來，並在 STATUS 寫明新 session 怎麼取得那個檔——否則搬進 repo 之後，新 session 照樣卡住。**新增一道閘門（或任何「以後都要這樣做」的規則）時，同時盤點所有教人怎麼做這件事的地方**——`CLAUDE.md`、README、STATUS 裡的每版流程、規格與工單範本、已執行的舊規格與工單（在檔頭加一句指向閘門即可）——一起改成指向閘門；只改規則、不改這些地方，規則生效了、入口還開著，新 session 照著 `CLAUDE.md` 做就繞過閘門。改過閘門就把「分別製造每一關的失敗」那組驗法重跑一次；驗法也寫成 repo 裡的腳本（§5.15 的登記制要靠它）。

   （2026-09-23 查了四個 Session 的推送那一行，沒有一個是乾淨的：三個在自查後面接了 `| tail -1`，自查失敗被吞掉，其中一次一個 commit 帶著自查命中被推上去；另一個的自查是好的，但在推送後面接了 `| tail -1`，推送失敗時，後面的線上確認照樣對著舊版跑。幾次都剛好沒有個資。）

## §5 測試紀律

1. **每條新斷言都要證明它會紅**：把對應邏輯改壞（突變），或拿修正前的程式跑，測試必須失敗；修回去必須綠。修 bug 時補一條「修正前會紅」的回歸斷言，並說明既有測試為什麼沒抓到。有新行為就補斷言。
2. **不寫假斷言。** 抓到過的形狀：母體是空的；母體恰好是「有問題的那幾個」；等待條件在上一頁就已經成立；反例太弱、被別條規則順便擋掉；掃描器把註解當程式碼；「應該是 0」旁邊沒有「母體非空」；斷言「某個東西不見了／被刪掉了」，卻沒先確認它原本在（先放一份，再驗它不見）。 斷言「它會失敗／會停下」只比對回傳值——別的原因也會得到同一個回傳值，把被驗的那一步拿掉照樣成立；盤點一整批時，常有一半的格子其實是別的規則擋的。要比對失敗的理由，被別的規則碰巧擋下的算「沒擋」。判斷「有沒有改動」別用會自己換模式的指令（`git diff --quiet` 在 repo 外會改成直接比兩個路徑、回 1，跟「有改動」分不出來；用 `git status --porcelain`）。「A 跟 B 一樣」的斷言，沒先證明 A 與 B 是兩個不同的來源、而且都非空——拿自己跟自己比、兩邊都抽到 0 筆，「一樣」永遠成立。寫完一條 `noneOf`／`everyOf` 就問一次：**這個母體現在有幾個元素？** **母體用登記制，不用排除制**：「只有登記過的才算」（例如讀測試鏈），不要「全部都算，除非有人記得排除」——排除制每加一個新東西就要有人記得一次，而那個人不會記得。 登記制要配孤兒檢查：該登記卻沒登記的（例如新加的測試檔、新加的建置腳本）要被報出來，否則只是把「記得排除」換成「記得登記」。 註解不是斷言。
3. **任何檢查類程式（掃描、閘門、斷言、驗法，包括一次性的搜尋指令）都要附對照組**：故意塞一個該被抓到的樣本，證明它會紅。**沒有對照組的檢查一律當成沒有檢查，不得當作「已驗證」的依據。** **判斷「過了沒」的那一層本身也是檢查**：跑測試的程式（runner）、共用的斷言函式、統計結果的稽核器、驗法本身——它們說「全過」，也要有一個必定失敗的對照（塞一條必敗的測試、餵一份必不合格的統計、給驗法一個必定不符的情境），證明它會報失敗。（v9 這一句被四個 App 都讀成只指掃描器；四個 App 的 runner 或稽核器都曾在某種情況下無聲地回報通過。） 反覆要跑的檢查寫成附對照組的腳本（每次先跑對照組，對照組沒命中就停），列進固定步驟；一次性的指令，要在同一次執行裡帶著對照組。**斷言驗語意、不貼字面。** 對照組**一定要有**自己造的合成樣本，而且跑的是同一個檢查（同一個搜尋式、同一段程式）；真實資料可以當第二道對照，不能單獨當對照組——它會隨時間變（實例：公開前自查的 email 對照組用 git 歷史的作者信箱，改用 noreply 之後就被排除規則濾掉、命中 0；路徑類的對照組去搜本 App 的 `CLAUDE.md`，那些路徑清掉之後，目標與對照組都是 0 命中，自查看起來正常、其實早就失效；「預期只命中本檔這一行」這種寫法，本檔那一行只碰得到其中幾個分支，其餘分支壞了也看不出來）。**每一類、每一個分支都要有自己的合成樣本。** 真實資料當第二道對照是必要、不充分：還要做突變（實例：規則分大小寫，真實原文剛好是小寫，對照組照樣全過，把壞寫法放進去的突變才抓出來）。補的對照樣本要真的落在盲點上——改回舊寫法照樣抓得到的樣本，等於沒守住。**一條規則有幾個分支，就要有幾個樣本；而且要證明每個樣本打到的是它自己那一支**：逐一拿掉每個分支，那一支的樣本就必須抓不到——否則它可能是被別的分支順便抓到，那一支壞了也看不出來。（MealMate 2026-09-25 自查：接管線 7 個分支原本只打到 2 個、斷言不存在 6 個打到 3 個、讀環境變數 14 個打到 7 個——大約一半的分支從沒有任何樣本；改成每次跑都逐一拿掉分支，當場又抓到兩件。統籌工作區的壞寫法掃描第一類 10 個分支原本只打到 1 個。**JLPT 逐分支補樣本時抓到一個真的漏洞**：路徑樣式的第三個分支少跳脫，不帶磁碟代號、以反斜線開頭的使用者目錄寫法一直抓不到（這裡照同一條規則只寫描述、不寫原樣）——帶磁碟代號的會被別的分支順便抓到，所以整條規則看起來有在作用。個資掃描有一種寫法從來沒被擋過，不是整潔問題。StockDiary 的數字最完整：壞寫法掃描「接管線」9 個關鍵指令只打到 4 個、「斷言不存在」4 個分支的樣本兩兩重疊；自查金鑰 4 種格式只測 1 種；建置驗法「堆疊那一行不帶括號」沒有樣本——模組頂層崩掉時的堆疊正是那個樣子，改成必須帶括號照樣全過，是真的漏洞。補了 46 條、每條只紅它自己的樣本。）**樣本之間不得共用零件**：一個樣本只依靠被測的那一個分支——共用了，拿掉一個分支會連帶弄紅別的樣本，「只紅它自己」就驗不出來（StockDiary 第一版踩到）。真的造不出只打到它的樣本的分支（被另一個分支完全包含），寫明理由、不做突變。

    **要寫出「被擋的東西」時，不要原樣寫下來**：對照樣本、證據檔裡的分支清單、規則說明，都要提到那條規則要擋的內容——原樣寫下，寫規則的那一次就違反了規則。用描述，或在執行時拼接（JLPT 收尾時把金鑰前綴與使用者目錄路徑原樣寫進證據檔的分支表，被自己的閘門擋下；MealMate 的合成樣本在執行時才組出來，是同一件事的另一面）。
4. **從使用者實際會走的入口測**：每個功能至少一條斷言從真實入口（畫面上的按鈕、對外的函式）進去，不能只驗內層純函式。
5. **寫檔、改檔一律用 Write／Edit 工具；shell 只用來執行指令**——不經 shell heredoc、`node -e`、`echo >`、`sed -i`，**不先判斷「這段有沒有特殊字元」**。（v11.5 改：v5–v11.4 寫的是「含 regex 或反斜線的測試碼、補丁，一律用 Write／Edit」，要人先判斷有沒有特殊字元；2026-10-02 四個 Session 各違反一次，都錯在那個判斷上——含反斜線或 regex 的補丁寫進 heredoc，`\n` 變成真的換行，把檔案寫壞。所以取消那個判斷。）`\s` 變 `\\s` 或被吃掉都不報錯、測試照樣綠、但永遠不命中。**搜尋樣式也一樣**：含反斜線或 regex 的樣式不要寫在 shell 指令列上傳給 `grep`、`sed`，寫進檔案或用程式語言直接寫——樣式被 shell 改寫之後，那道搜尋永遠不命中、也不報錯，一直是空轉。 **已知限制**：§5.16 的機器掃描只看得到寫進檔案的內容；即時打在指令列上的 `node -e`、`python -c`、heredoc 看不到。這一條目前**仍然只靠人記得**——而四個 App 與統籌工作區都一再違反（規則寫在文件裡擋不住，這一條還沒交給機器）。能交給機器的做法是在指令執行之前攔下來檢查（例：開發工具的「執行前」掛勾），但那是持續生效的設定，要先經同意才加。（統籌工作區 2026-09-25 經 Dispatch 同意試裝，結果見下面「試裝結果」；四家要不要照做，會改變做法，屆時送 Yolin。）

   **耗時很久的整套（突變整套、全面檢測）**：等一批交辦事項做完再一起跑、一起看（Yolin 2026-09-19），不必每版跑、也不照固定天數。全跑只在 §5.18 第 3 點的三種時候；Session 不自己開跑，時機由 Dispatch 排（§5.19）。各 App 在自己的 STATUS 寫明「整套」指什麼、實測要跑多久、以及上限（距上次整套幾版、幾條突變或新斷言從未整套跑過）——上限照本 App 整套的成本訂：要跑幾小時的訂緊一點；只要幾分鐘的可以訂得很寬，或乾脆寫「每版都跑整套、不需要上限」。耗時還沒量過就寫「待量」，不要猜；超過上限時，回報最前面用一行講出來並建議「這一批做完就跑」，沒超過不必每次提。**成本算對地方**：整套是機器在背景跑，花的是時間，不是 token；花 token 的是處理結果的來回——所以要省的是「處理的次數」，結果一次回報、依根因分組。回報寫明是在哪個 commit 上跑的；沒紅的先在最新版複驗再處理。**整套的證據要進 repo**（Yolin 2026-09-23）：每次跑完，把日期、commit、範圍、條數、結果、耗時、沒紅的清單寫進 STATUS 或一個進版控的摘要檔——只存在本機 log 等於沒有紀錄。**完整的 log 寫到 repo 底下、被 `.gitignore` 擋掉的目錄（例如 `.logs/`）**，檔名帶日期與 commit；不要寫在系統暫存目錄或 session 的暫存區——跑好幾個小時的整套，啟動它的 session 可能中途被關掉，暫存目錄會跟著消失。**入庫的證據要能複核**（2026-10-02：JLPT 有 29 條突變的證據只剩「紅 13、14」這種總數，原始 log 在 Session 暫存區、已經不在，只能降級成「曾有紀錄、無法複核」）：原始 log 寫進 `.logs/`、不進版控（完整 log 可能帶本機絕對路徑，§2.4）；**入庫的證據檔由腳本從 log 產生，而且逐項**——每一條一行，帶分類（含「情境未成立」，§5.20）、預期紅哪幾條、實際紅哪幾條；**只留總數的證據等於沒有證據**；產生腳本入庫，做路徑與個資清洗，清洗配**雙向**對照組（含路徑的那一行要被洗掉路徑；分類、預期、實際不能被一起洗光）；母體檢查：證據檔的行數等於這次跑的條數，不等就點名、回非 0、不寫檔。**耗時數字進版控**（沒有個資也沒有路徑）——否則換一台機器，§5.19 的按次預測永遠從零開始。**刪一條突變之前，要能說出這段程式為什麼在任何真實路徑上都走不到**；說不出來，就是測試走錯路，要改的是測試。
8. 隨機或情境敏感的輸出（排程、排菜、抽樣）不得綁死單一結果。需要特定情境才分得出對錯的斷言：優先自己造情境、直接呼叫被測的函式；若用整段產生的結果，先寫一條前置斷言確認情境存在，不成立就紅。**固定 seed 不算釘住情境**（資料或規則一改，同一個 seed 的結果就變）；沒有前置的「至少 1 個」就是假斷言。前置斷言自己也要用突變證明會紅（把情境拿掉，它必須紅）。統計型斷言另照各 App 的做法（多組種子量餘裕）。沒有單元測試層、只有端對端測試的 App，「自己造情境」就用它造得出來的方式（預置儲存狀態、URL 參數）；前置斷言照樣要。
9. **突變的 `expect`**（有這個機制的 App）：`expect` 是用來確認「紅的是指定的那一條」，所以**不要寫會變動的數字或整句訊息**——斷言訊息一改，突變就變成「紅錯地方」。訊息本身沒有穩定的開頭時，不要把 `expect` 寫鬆，而是**在訊息前面加一個固定標籤當錨點**（例：訊息寫成「早餐道數門檻：早餐 N 道…」，`expect` 比「早餐道數門檻：」）。改任何斷言的訊息時，一起搜突變清單裡含舊文字的 `expect`。秒級的突變檢查要同時查「`expect` 在對應測試的原始碼裡找得到」，不必等整套才發現過期；還沒有這個檢查的，列進本 App 的待辦，下次動突變機制時補。
10. **加資料之前，先查畫面上依筆數寫死的上限**（例如選單只列前 N 筆）：新加的資料可能永遠排不進畫面，卻沒有任何測試會紅。有這種上限的，加完要有一條斷言從畫面數得到新資料。
11. **驗一個檢查器或閘門時，光確認「它擋下來了」不夠**，分四層，缺一層就可能是假驗證：
    - **是誰、為什麼擋的**：預期失敗的情境，要比對失敗的內容與位置（輸出裡哪一關、哪一支、哪一類、哪個檔），不能只比對回傳值——同一個回傳值可能是別的原因造成的，甚至是驗法根本沒跑。造情境的步驟（例如測試用的 commit）失敗就中止，不要帶著沒造成的情境往下驗。 會擋的結論要成對驗：造一個漏洞，看它紅；再把「造情境」那一步弄壞，看它不會變成恆真。這一層對驗收者自己一樣適用——驗收者自己寫的探測，也常是回傳值對、理由不對。**加了一道新的擋之後，回頭查既有的情境有沒有變成「照樣綠、但理由不同」**——不是一開始寫錯，是後來的改動讓它變錯（MealMate：加了 GIT_ 入口拒絕之後，原本用 `GIT_DIR` 造失敗的情境照樣綠、擋下的卻變成入口拒絕）。比對理由的字串要帶到分得出來的程度：統籌工作區的情境 K 用不帶類別的「命中  檔名」比對，自查對每支改到的檔都印一行「零命中  檔名」，於是不管為什麼擋都判符合——突變清單的預期把它抓出來。
    - **擷取那個資訊的程式本身也要有對照組**：它若抓空，「比對是誰擋的」就默默退化成只剩回傳值。拿一段已知的輸出餵給它，確認抓得到該抓的那一句。
    - **驗法的對照組要確認真的作用在被驗的對象上**：把被驗的東西改壞一處，驗法必須報不符；而且要確認改壞的那一份真的被執行到——複本、分支、路徑對錯了，壞的那一份根本沒跑，驗法照樣全部「符合」。還要確認**讀到的輸出是這一次產生的**：跑之前刪掉舊的輸出檔；對照組兩個方向都驗（應判相同的要判相同、應判不同的要判不同）。「沒執行」跟「預期結果」長得一樣時，只看結果永遠分不出來。 改動沒套上就不跑、不讀輸出。突變、盤點、驗收之前，先在同一個環境跑一次原樣、確認是綠的——原樣就紅，後面「改壞之後紅了」都不能採信（在暫存複本或拋棄式 worktree 裡做時，主工作區還沒 commit 的改動不會跟過去）。所以**推上去的每一個 commit 單獨 checkout 都要是綠的**：程式與它牽動的文件數字、測試放同一個 commit。拿「修正前的版本」來比，先證明它真的是舊版：用明確的 commit 雜湊取，確認內容跟新版不同、新版才有的標記只在新版（worktree 或複本的來源若指向本機 repo，「舊版」可能其實是新版）。
    - **情境之間互不污染**：一條紅要說得出是被哪個缺陷弄紅的。一個情境把東西真的推出去之後，後面的情境可能紅在別的理由上（例如推送被拒）——那不算抓到。每個情境跑完，把它動過的共用狀態（測試遠端、本機追蹤分支之類）還原成開始前的樣子，順序改變也不影響結果。 一種情境紅了，也不能讓整輪中止：還原的步驟要能處理「該發生的沒發生」（例：預期推得上去卻沒推上去，測試遠端就沒有那個 commit 可以撥回去）。**這個洞平常看不到，因為平常不會紅；真的紅了，你會以為「只紅這一種」，實際上是「紅在這一種，後面的都沒驗」。** 所以判定時要先確認每一種情境都有結果，少了就算驗法出錯，不算「其餘都過」。

    （2026-09-23 的實例：一個 App 的驗法有一種情境回傳 1，擋下它的卻是另一類檢查——造情境的 commit 沒做成，合成字面又被另一類掃到；另一個 App 有去比對「是誰擋的」，但擷取擋下原因的樣式沒對到巢狀括號，前兩種情境抓空、只剩回傳值；第三個 App 的三種壞閘門都「回傳 1」，卻沒有任何一種情境報不符——驗法複製過去推的是 `main`，不是當時的 detached HEAD，壞閘門根本沒被執行到。）

12. **突變之後照樣全綠，先分辨是等價突變還是測試無力**：先問「這個改動有沒有改變行為」，再問「測試是不是不夠力」——順序反過來，就會為不存在的洞補假斷言。一個行為由兩道東西共同守著時（例：先抓遠端、再用它算範圍；照結構抽行、再用另一個來源核對行數），單改其中一道會被另一道補上，看起來像沒驗到。把「只改 A」「只改 B」「兩個一起改」擺在一起看，只有真的會漏的那一種必須紅；確認是等價突變的，寫明理由，不為它補斷言。

    **每一條突變寫明預期紅哪一種**（有 `expect` 機制的照 §5.9），判定「紅的正好是那一種」——沒寫就判不出紅錯地方。判定之前先確認每一種都抽到了：**「沒抽到」和「抽到但沒紅」在結果上長得一樣**（統籌者的判定器第一版有 9 種對照樣本，就缺「預期要紅的那一種根本沒抽到」，拿判定器自己做突變才查出來）。突變本身不能帶進會被其他檢查抓到的寫法（例：用 `|| true` 關掉一個條件，會被壞寫法掃描擋下、紅在別處；只看「測試回 1」會誤判成突變被抓到）。

    **N 條規則要有 N 個不同的擋法**：逐條單獨拿掉，各自只紅自己那一種。做不到，常常不是測試寫法的問題，是幾條規則共用同一道擋——那只有一道防線，要改設計，或照實寫明。所有規則共同依靠的一環（例：閘門整個不理某個結果）另列、自己一條突變。證據附一張表：規則 → 靠哪一個擋法 → 只紅它的那一條突變。

    **先分清楚共用的是哪一層**（MealMate 2026-09-25 的限定）：一個擋法可以拆成「偵測」（有沒有取到那個來源、看不看得出問題）與「處置」（看出來之後停下）。**偵測共用**——好幾條規則其實靠同一個判斷看出問題——才是真的只有一道防線，要改設計或照實寫明。**處置共用、偵測各自獨立**（例：各種來源各自取、各自比對，最後都交給同一句「有命中就停」）不是防線變少，不必改設計；但表上要證明偵測那一層每一種各有一條只紅它的突變，處置那一環另列、自己一條突變。某一種情境就是那一環的基本情境、沒有只屬於自己的擋法時，照實寫「沒有」，不要為了讓表好看硬湊一條突變。**「會擋」與「會放」是同一個判準的兩面，用同一個比較器是必然的，不算偵測共用**（TripQuest 2026-09-25）：同一道比對「抓到不同就擋、全部相同就放」，要同時驗會擋與會放，本來就只能用同一個比較器；為了「不共用」拆成兩個比較器，反而可能彼此不一致。這種情況表上照實寫明，兩邊仍各配一條只紅自己的突變（例：「只比第一支」只紅會擋那一種、「相符也擋」只紅會放那一種）。兩道偵測互為備援時，只拿掉一道是等價突變、不會紅，兩道一起拿掉才紅，照實寫明（TripQuest 同一輪）。**兩個來源不得用同一個情境同時覆蓋**：例如作者信箱與提交者信箱——用 `git -c user.email=…` 造 commit 會讓兩個同時是一般信箱，拿掉其中一欄的掃描、另一欄照樣抓到，突變不紅。各自一種情境（只有作者是一般信箱，用 `--author`；只有提交者是）、各自一條突變。（2026-09-25：MealMate、JLPT、統籌工作區三個實作都中——前兩者兩欄一起設，統籌工作區只驗了作者；JLPT 的第二道「欄位不能空」也只驗了作者那一半；StockDiary 實測：自查改成不取提交者信箱，23 種情境裡 22 種照樣符合——**四家與統籌工作區全中**。）**來源標註也要分開**：自查把兩個來源標成同一個名字（例：作者與提交者都標成「作者欄」），就分不出是哪一邊抓到的，情境再分開也驗不出來（TripQuest 的根因；四家全中，根因兩種：情境讓兩邊同時是一般信箱，或標註把兩邊當成同一個來源）。**筆數檢查不等於內容檢查**：「作者欄的行數等於 commit 數」證明欄位取到了，不證明兩欄的內容都有被掃（StockDiary 自己更正先前的說法）。

    **隱式的擋**（沒有另外寫的「停」，靠例外沒被吞掉、靠「讀不到就等於不一樣」擋下的）拿不掉一個停；突變改成把那段邏輯弄成放行——吞掉例外、讀不到當成一樣、空值當成 0 命中。
13. **檢查器故障時，預設是停下，不是放行。** 算不出來、解析不了、取到的是空的，都不能當成「0 個命中」「沒有問題」。能用另一個來源核對的就核對（例：抽出的新增行數要等於 `git log --numstat` 算的；有 commit 就一定有作者欄），對不上就停，並講明是「檢查器壞了」而不是「有命中」。要找的寫法：失敗就 `continue`、`|| true`、`catch` 之後當成空、讀不到就給 0 或空字串、兩個指令接管線。**拿「0 命中」下結論時，寫下查了什麼、查了多少**（範圍、行數）：少查一段，結果照樣是 0。

    **失敗分支要有常設情境**：「取不到就停」「沒全過就刪登記」這類分支，正常情況永遠走不到，最可能壞了沒人知道。**「證據裡實跑過一次」不等於有東西守著**——改壞了要有一種情境會紅。造失敗用假的依賴：shell 腳本在 `PATH` 最前面放一個只讓指定子指令失敗的假指令；程式把外部依賴（git、檔案系統、子程序）當參數傳入，測試傳會失敗的版本；或讓真的依賴失敗（例：`GIT_DIR` 指向不存在的目錄）。假的依賴自己要有對照組（指定的必須失敗、不相干的必須照常）。**正式程式不留測試用的開關**：不准有「設了某個環境變數就故意失敗、或關掉某一類檢查」的後門——它現在也許有對照組兜底，對照組哪天被改壞，它就變成關掉檢查的開關。**這類開關的名字通常是中性的、用途也真的存在**（例：讓驗法換成一支壞掉的檢查器，名字叫 `PRECHECK`，看起來像設定），所以不能靠「看起來像不像後門」判斷，**要靠有沒有登記**：正式程式讀的每一個環境變數都要登記在案，沒登記的一律報——包括「賦值時先讀自己」（`X="${X:-預設}"`）這種寫法。（2026-09-25：統籌者讀程式判斷「另外三家沒有這種開關」，StockDiary 自己用規則掃出 `PRECHECK`／`PIISCAN`——統籌者當時的搜尋式只抓名字像測試開關的變數，而且 shell 那一支沒有對照組。「讀程式判斷沒有」不等於「證明沒有」。）

    **環境變數分兩類，做法不同：**
    - **程式自己讀的**（`process.env.X`、`os.environ`、shell 裡讀了卻沒賦值的變數）→ 登記制＋機器掃描：只准登記過的，其餘一律報。
    - **底層工具自己認得的**（git 的 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE`……；bash 的 `BASH_ENV` 與匯出的函式；node 的 `NODE_OPTIONS`；Python 的 `PYTHONPATH`）→ **程式碼裡什麼都看不到，掃描找不到**，只要剛好設在環境裡，閘門就可能對著另一個 repo 跑完全套檢查、然後說通過。**只能在入口主動拒絕**：**每一個能單獨被執行的入口都要擋**（閘門本身、會單獨跑的自查、掃描、驗法），在各自第一個 git 指令之前檢查，有就停；要擋哪幾層因 App 而異（git、bash、node、Python……看那個入口實際會叫到誰），**不要寫死層名**（JLPT 的另一層是 Python、不是 node）。**比對不分大小寫**：Windows 的環境變數名稱不分大小寫，小寫的 `git_dir` 對 git 來說就是 `GIT_DIR`（統籌工作區 2026-09-25 實測；MealMate 先抓到）。git 的用前綴擋（`GIT_` 開頭一律擋，只放行登記過、不影響「看哪個 repo、推去哪」的幾個，例如 `GIT_EDITOR`——開發工具自己就會設它，不登記會誤擋每一次推送）；每一類一個分支、一種情境、一條只紅它的突變；另有一種「只設了登記過的」要照常放行的情境。**列不完的照實寫成已知限制，不要假裝窮舉**：`PATH` 前面放一支假指令、git 的全域與系統設定檔（例：`url.<x>.insteadOf` 可以改寫推送目標）、`BASH_ENV` 在閘門第一行之前就已經被執行過。

    **「讀程式碼搜過、沒找到」一律寫成「在搜的樣式範圍內未見」，並寫明搜了什麼樣式、母體是什麼**——搜的樣式照名字篩會漏（中性的名字）、有一整類根本搜不到（底層工具自己認得的）。真的造不出來的，列為已知限制，寫明理由與替代的證明。
14. **新增或擴大一道「對不上就停」的檢查之前，先拿真實資料實跑一次**（例：最近幾十個 commit），確認正常內容不會被擋死；並補一種「正常情況要放行」的情境（例：只刪不增的推送）。真實資料上新舊寫法一致，只證明不會誤擋，不證明新舊一樣對——歷史裡可能剛好沒有會觸發的內容。 擴大範圍的修補（例：挑哪些檔來掃），用新舊兩版對同一個母體各算一次，證明沒有少挑。
15. **寫明每一個檢查什麼時候會跑**（每次推送、每版、全面檢測、手動）。很久才跑一次的，中間就是盲區，要寫明盲區多長。「改過就要重跑」這種規則，能做成機器擋的就不要靠人記得（例：驗法全過時登記被驗程式的雜湊，推送前比對，對不上就不推）。 跑很久、不適合每版跑的驗法，接進推送閘：驗法全過時登記它守的每一支檔的雜湊（登記不進版控），推送的 commit 動到那些檔、而登記不在或對不上，就擋下並點名要先跑哪一支驗法；沒動到就不看登記。**登記的是實際被驗過的那一份內容**，不是工作區現在的狀態：被驗的每一支（含驗法自己）在開跑時存下內容或雜湊，登記前跟 HEAD 比，不同就不登記——只比開跑與跑完時的工作區，中途改了又改回去就騙得過。驗法一開跑就刪自己的登記、全過才寫回；只跑了部分情境不登記。
16. **好幾個 App 都通過同一種檢查，不等於那種檢查可靠。** 各自的實作常是同一個慣用寫法被複製了好幾份，會在同一處一起出錯（實例：`git log -p --format=` 把 commit 訊息與作者欄整個拿掉；「以 `+++` 開頭就跳過」把內容以 `++` 開頭的新增行也丟掉——兩次都是四個 App 同時中）。複製來的一致只算一次；各自遇到問題、各自想出同一個解法的一致，才是獨立的證據。找這類洞，拿**只落在那個寫法盲點上的樣本**同時去試每一個實作。
    同一個人也一樣：規則寫下、甚至親手修過，下一次寫新程式還是會寫出舊寫法。所以**已知的壞寫法要做成機器掃得到的**：各 App 的常設檢查（每版會跑的那一組）加一條，掃自己的閘門、自查、驗法腳本有沒有下面這幾種；這一條本身也照 §5.3 要有合成的對照組（一段已知的壞寫法必須被抓到），並先在現有腳本上確認不誤報：
    - 自查、推送、取遠端狀態、取 diff 的那一行後面接管線（`|`）
    - 自查或閘門裡的 `|| true`、空的 `catch`
    - 用「以 `+++` 開頭」判斷 diff 檔頭
    - 同一支腳本用 `--format=` 取新增行，卻沒有另外取 commit 訊息與作者欄（`%B`、`%ae`）
    - 斷言「不存在」（`false`、`!exists`、「不見了」）的地方——機器只能初篩，命中的逐條看前面有沒有「先確認它原本在」
    - `grep`、`sed` 的樣式含反斜線、寫在 shell 指令列上——初篩，命中的逐條確認它在同一次執行裡跑過對照組
    - 正式的閘門、自查讀了哪些環境變數——只准登記過的（例如取本機使用者名稱），其餘一律報（§5.13 的後門）；對照樣本要含「賦值時讀自己」的寫法（例：`X="${X:-預設}"`，MealMate 第一版就躲過）
    **登記的例外只能在實際命中、逐行看過之後補登**，並寫理由；不要預先猜哪幾行會需要例外（三個 Session 各自預寫過，一條都沒命中）。例外沒命中任何一行也要報——過期或猜錯。**例外登記的顆粒度要跟規則的分支一致**：登記的是「這一行的這一類（這一個分支）」，不是「這一行」或「這一類」——否則登記一次就把整類放行（MealMate：間接讀取整類只登記一次，之後再加哪一種讀法都放行；統籌工作區：例外只比「檔＋那一行」，同一行上任何一類都一起放行，已改成每條例外寫明放行哪幾類、並有對照組）。**一條例外只准對到一行**：要有檢查要求「剛好一行」，比對的那一段字要夠具體——StockDiary 16 條例外現在各對到 1 行，但沒有檢查要求剛好一行，其中兩條的比對字很通用（像「`node -e \"`」這種開頭），同一支檔以後再加一行同樣開頭的壞寫法會被一起放行。
17. **產資料的建置腳本（把來源整理成 App 讀的資料檔）：來源變少或不見時，全部停、一個檔都不寫。** 「留下舊輸出」與「寫出空輸出」都比報錯危險——App 讀得到檔，表面一切正常。寫任何檔之前，從登記清單確認每一個單位都有來源、有效筆數（過濾、去重之後）不低於登記的下限；缺任何一個，列出全部問題、回非 0、一個檔都不寫。寫檔先寫暫存、全部成功才一起換上。跟上一次成功的輸出比，筆數降幅超過登記的比例也停；真的要縮減，用明確的參數表達。停下的理由點名單位與哪一種。驗法的母體是「每一個單位 × 每一種情境」，不挑代表；每一格要同時成立：回非 0、輸出點名那個單位與那一種、輸出目錄（含清單檔）前後雜湊相同。
18. **突變平常只跑受這次改動影響的；全跑另有時機；每一條都要有帳。**（Yolin 2026-10-01，指名全部 App）理由：整套一跑好幾個小時就常跑不完，跑不完的那幾條就一直沒被執行——一道從沒被執行過的防線，跟沒有防線一樣（MealMate 的突變整套 492 條、約 5.3 小時，有 50 條從沒在整套裡跑過）。**沒有突變清單的 App**（突變是每條新斷言當場手動改壞）：第 1–4 點照 §0.5 寫「不適用」與什麼時候回頭照做；第 5 點一律適用。
    1. **預設只跑受這次改動影響的突變，範圍從實際的 `import` 關係圖算**，不從手寫的分類算。**預設從寬**：關係圖只要沾到就跑——直接或遞移引用了被改的檔、對應的測試檔本身被改、突變執行器或測試共用工具本身被改。**判斷不出範圍的一律全跑**：動態組出來的 import 或讀檔路徑、改到不屬於任何已知類別的檔（資料、設定、`package.json`、建置腳本……）、關係圖工具讀不到檔或解析失敗。**讀不到、解析不了，不是「沒有關係」**（§5.13）——「讀不到就跳過」會讓範圍變小、結果照樣全綠。寧可多跑，不可少跑。手寫的放大規則（某些檔一改就擴大範圍）可以加，只准讓範圍變大、不准變小。**要縮小範圍**（例：某類檔一改就放大成全套，想給它一條較窄的規則），那是從寬變嚴的方向，要三件：寫**正確性的依據**（那些檔實際會影響什麼），「跑全套太慢」是成本理由、不算依據；**配一條突變**證明縮小後還抓得到（故意弄壞被它涵蓋的行為，縮小後挑到的那組測試仍要紅）；**反向也要**（原樣時要過）。縮小後抓不到，就維持放大。（TripQuest 2026-10-02：想給 `tools/ev` 的 `.sh` 補一條規則，免得每次動到就放大成全套 57 支。）
    2. **挑選器本身是檢查，要有對照組**（§5.3）：故意把分類弄錯，必須有東西紅——否則「跳過」就是一條永遠不會紅的捷徑。做法：用假的檔案系統或固定的樣本餵挑選器，答案事先寫好；第 1 點每一條從寬的規則各一種樣本（遞移兩層以上的引用、每一種 import 寫法、動態路徑、讀不到的檔、未知類別的檔、執行器或共用工具本身被改），各配一條只紅它的突變（例：只展開一層、讀不到當成沒有關係、漏認一種 import 寫法、未知類別當成不受影響）。每次跑都印出「跑幾條、跳過幾條、為什麼全跑」，並能只列不跑、逐條列出跳過的理由。
    3. **全跑只在三種時候**：Yolin 明講要全面檢測；發布較大的版本之前（什麼算「較大」由本 App 在 STATUS 寫明）；改動大到關係圖判斷不出範圍（第 1 點）。全跑屬於重負載，時機由 Dispatch 排（§5.19）。
    4. **要記「上次全跑」的帳**：每一條突變答得出「上次在整套（或分段補跑）裡跑過是哪一天、哪個 commit、紅了沒、紅的是不是預期那一種」；**從沒在整套裡跑過的，一行指令列得出來**；帳本是進版控的檔，由執行器跑完一條就寫，不手改。只有算數的結束才記——逾時、被殺、沒跑起來，不算紅，也不算跑過。帳本要配孤兒檢查（§5.2）：清單有、帳本沒有的算從沒跑過；帳本有、清單已經刪掉的要報。§5.7「幾條從未整套跑過」的上限從帳本算。
    5. **新寫的防線一定當場證明會紅**（§5.1），不因為「平常只跑受影響的」而省：新斷言、新突變、新檢查，寫好就單獨跑那一條，確認它紅、而且紅在預期的那一種。這一步才是突變測試真正有價值的那一步，而且便宜。
19. **重負載的資源上限（專案不得放寬，§0.3）。**（Yolin 2026-10-01 經 Dispatch，指名全部專案）**Yolin 的機器是筆電。平行度的上限不是效能問題，是不要讓他的機器卡死到連工作管理員都開不了**——出事時他沒有自救手段，只能硬關機。（2026-10-01：一個專案一次開 160 個 node 程序、實測每個 88～98 MB，合計要 15.7～20 GB，那台可用記憶體只有 7.4 GB；兩個專案的重工作同時跑，當天硬關機兩次。）
    - **重負載的定義（v11.5 修正）**：**重負載 ＝（2 個以上工作程序，且這一次預估超過 60 秒）或 任何這一次預估超過 600 秒 或 任何會開瀏覽器的套件。** 重負載**開跑前向 Dispatch 要許可**；許可一次一場、不累積，跑完（或中止）回報，讓 Dispatch 放下一個。**其餘照跑、不用許可，但要記進資源紀錄。** 這條規則的本意是防筆電過熱關機；v11.1–v11.4 的定義只看程序數，照字面連 2 個程序跑 43 秒都要許可，那不是本意。**不要拿新定義回頭把舊的場次記成違規**——那會讓紀錄失真。
    - **兩條例外**（§0.3 不得放寬的範圍連它們一起）：
      - **秒級的單支檢查**（例：語法檢查、單支掃描）：不需要許可，照跑，但要記進資源紀錄。
      - **常規測試套件**（這一次預估不到 600 秒、不開瀏覽器；例：每版跑的測試鏈）：**不排隊、不需要許可；部署前必跑**——本 App 規定的部署前測試是閘門，不是可選項，不得因為排隊而跳過或延後。照樣記進資源紀錄。部署前的測試若這一次會開瀏覽器或預估超過 600 秒，就屬重負載：**照樣必跑、不得跳過**，只是開跑前先拿許可。
    - **歸類按「次」，不按指令名稱**：同一個指令每一次的耗時可能差很多（TripQuest 的 `test:affected` 實測從 111 秒到 1109 秒，取決於那次挑到 52 支裡的哪幾支——挑到單支 516～580 秒的 `layouttest` 就超過 10 分鐘），所以「這個指令屬常規還是重負載」沒有答案。**每一次開跑前，依這一次的實際範圍（挑到哪幾支、哪幾條）預測耗時**，用每一支、每一條自己的實測耗時加總；預測超過界線就照重負載要許可（常規測試套件預測超過 10 分鐘也一樣，部署前照樣必跑，只是要先拿許可）。範圍裡有沒量過的單位、或預測不出來，就當成重負載——量的那一次要許可。
    - **預測要被回頭檢查**：每一次把「預估」與「實際」一起記進資源紀錄。只信預測、不回頭對，預測器壞掉時不會有任何東西紅——它只會一直預測「這次很短」。所以偏差要被看見：**連續 3 次實際超過預估 50% 以上，或任何一次實際越過界線而那次沒拿許可**，就要改預測法，改好之前那個指令一律當重負載（本 App 可以訂得更嚴，不能更鬆）；回報與整套證據附上最近幾次的預估與實際。預測器本身是檢查（§5.3）：餵一組事先寫好耗時的範圍，預測必須越過界線；把某一支的耗時改成 0 的突變必須讓這一條紅。
    - **全部專案合計同時最多 4 個工作程序，由 Dispatch 執行**：單一 Session 看不到別的專案開了幾個程序，只有 Dispatch 同時看得到所有 Session，所以合計上限靠「重負載開跑前要許可」來守，不是由 Session 自己算全機的數字。Session 自己守的是：**本 repo 同時最多 4 個工作程序**——測試、突變、檢查工具開出來的 node、python、瀏覽器實例各算一個（瀏覽器自己再開的子程序不另算個數，但記憶體要算進紀錄）；啟動它們的那一支主程式不算。上限寫成程式裡的數字（例：工作佇列最多 4 個），不靠「這次應該不會開太多」；不要照 CPU 核心數決定平行度。
    - **資源紀錄量的是本 repo 的**：固定間隔（例：每 60 秒；秒級檢查記開始與結束各一筆）把本 repo 的工作程序數、它們合計的記憶體、系統可用記憶體寫進 `.logs/` 的紀錄檔（跟 §5.7 的整套 log 放一起）；整套的證據摘要附上峰值。**不要寫成「全機」的程序數**——量不到的東西寫進紀錄，只會讓人填一個看起來合理的數字。紀錄本身照 §5.20：上線時先確認它在一個已知有程序在跑的時刻記到非 0。
    - **峰值用逐一計數，不用取樣**：開子程序時加一、結束時減一，取最大值；取樣降級成輔助，只量記憶體與 CPU。**兩種峰值並列印出**，差距就是那一場取樣漏掉的量。取樣間隔要比最短的那個工作短，否則是系統性漏算。（JLPT 2026-10-02：峰值記到「工作程序 1 個，大多數取樣行甚至 0 個」，比前幾次的 2、5 還低——短命的程序夾在 60 秒的取樣間隔之間，一次都沒被取樣到。TripQuest 雙向實測：逐一計數峰值 4，同一次取樣只有 1。）**環境與權限的限制寫進輸出**，不只寫在 STATUS（TripQuest 拿不到要管理員權限的程序建立事件，改用 0.1 秒輪詢，活不到 0.1 秒的程序仍可能漏計——它把這句印在結束行裡）。
    - **量測數字算錯寧可作廢，不要報一個偏低的數**：報 0 會讓調度的人以為那一場幾乎不吃資源。（TripQuest 的取樣器在 Git Bash 底下記到「工作程序 0、全部程序 1」——Git Bash 內部再開的程序父子關係接不起來，下面的 node 全部漏算——它把那一段的峰值作廢、沒有報 0；JLPT 同樣作廢。）
    - **PID 會被重用，認子程序要看建立時間；殺程序只殺清單裡的**：兩道都要——**子程序必須比父程序晚建立**；**只殺名稱在可殺清單裡的**，不在清單裡的就算被認成子程序也只印出、不殺。（JLPT 2026-10-02：資源紀錄把 OneDrive 的同步服務認成自己開的子程序——它的 PID 早上四點就在、父程序早就結束，新開的 bash 剛好拿到同一個號碼。TripQuest 查出它的 `taskkill /T` 真的可能殺到不相干的程序。可殺清單當天攔了三次真實的東西：OneDrive 同步服務、`wermgr.exe`、`powershell.exe`。）用 handle 殺自己開的子程序不受影響（StockDiary 確認過），用 PID 重新查的就有這個洞。**兩道互為備援，單獨拿掉任一道都不會有測試紅**——在程式旁寫明這是刻意接受的例外（§5.12 的等價突變），移除任一道之前先確認另一道還在。
    - **怎麼證明本 repo 的上限真的有作用**（§7.5(c)）：造一個會想同時開 10 個工作的情境（例：10 個只睡幾秒的假工作），從紀錄檔讀出的峰值必須 ≤ 4；把上限改成 10 的突變必須讓這一條紅。假工作只睡覺，屬於秒級檢查、不需要許可。
    - **限制平行度只是移除一個很可能的誘因，不等於修好了關機問題**：2026-10-01 第一次當機另有 bugcheck `0x9F`，指向驅動程式的電源狀態切換，跟負載是兩回事。不要因為加了上限就回報「關機問題已解決」。
20. **機制存在、但從沒被真的執行過，等於沒有機制。**（2026-10-01 一天裡第三次出現）三個實例：MealMate 有 50 條突變從沒在整套裡跑過；一個專案的「內容雜湊沿用」機制從沒被觸發過，所以一直沒被驗證；論文專案的全稱句掃描對 HTML 完全沒作用，卻回報「25 行 OK」——那 25 行全是 `.md`。共同點：看起來在運作，實際上從沒走到它該走的那條路。
    - **新的機制上線時，正反兩向各觸發一次**：該動作的情境真的動作了（跳過了、沿用了、擋下了），不該動作的情境真的沒動作；兩次都留下證據（輸出裡那一句、紀錄檔那一行）。只觸發過一個方向的，寫明另一個方向還沒被執行過。
    - **統計類的檢查（掃了幾行、幾個檔、0 命中）要先證明工具真的讀得到目標**：在同一個檔、同一種格式上先抓到一個已知會命中的樣本，再相信那個 0。結果要列出實際讀到的是哪幾類檔、各幾個——「25 行 OK」要分得出是 25 行 `.md` 還是 25 行 HTML。
    - **「對照組是合成字串」不算對照組**：把合成字串直接餵進內部函式，只證明規則的語法沒寫錯，不證明它讀得到、掃得到。**每一條檢查分支，對照組必須是它真正會掃的那一類真實檔、走真實的入口**——造一個那一類的檔（`.js` 分支就是 `.js` 檔、掃 commit 的分支就是一個真的 commit），從命令列入口跑，不直接呼叫內部函式。實例（JLPT、TripQuest 各自盤出同一種形狀）：JLPT 專掃 `.js` 的分支從來沒有 `.js` 樣本，照樣印「掃了 53 支、0 命中」；TripQuest 管線檢查有 `.mjs` 專用分支、樣本卻只有 `.sh`，跳脫掃描的 `.sh` 分支完全沒有樣本；推送前掃描有 12 個分支從沒在真的 commit 上驗過，只有 email 那一條走過真實的 git 抽取。**造樣本時，先確認寫進檔裡的那一行真的含有違規字串**：為了不讓寫樣本的程式自己被掃到而把字串拆開相接，寫出去的那一行可能根本不含違規字串（TripQuest 把 `||` 拆成兩段相接，寫進去的行其實不含 `|| true`，第一次因此沒紅）——寫完讀回那個檔、斷言違規字串在裡面，再跑檢查。**從命令列入口跑的對照組，在 repo 的暫存複本裡跑，不在工作區裡跑**（例：暫存目錄裡 clone 一份，做完整個刪掉）：這樣既走到真實的讀檔與入口路徑，也不必把樣本寫進真實的原始碼檔、沒有改壞原始碼的風險——每次推送都要跑的常設對照組也一樣（JLPT 2026-10-02 提出；它的自查情境本來就這樣做，這裡推到全部）。**跑完要比對工作區與 HEAD，確認沒有殘留**：跑之前、跑之後各取一次主工作區的狀態（`git status --porcelain` 與有改動的檔的雜湊），兩次必須相同；跑之前是乾淨的，跑之後就必須跟 HEAD 一樣乾淨。
    - **暫存複本必須含有這次要測的那個改動**：`git clone` 拿到的是已 commit 的版本，突變或樣本改的卻是工作區——不處理的話，複本裡跑的一直是沒改壞的程式，輸出照樣顯示「跑完了」（MealMate 2026-10-02：一組 3 條對照組因此從頭到尾測的是原版）。clone 之後把工作區的相關目錄覆蓋過去，或用別的方式確保改動在複本裡。**而且要驗，不能只靠流程**：在複本裡把那支檔讀出來，確認改壞後的那段字串或違規樣本確實在裡面，確認到了才算情境成立；讀不到就判「情境未成立」（見下）。**對照組沒抓到時，先查改動到底有沒有進到被測的那一份，再查規則本身**——不然會去修一個其實沒壞的規則。
    - **判斷結果類別不能用子字串比對**：「紅在哪一條」「這一行是過還是不過」要錨定在行首或固定欄位，不在整行裡找子字串；說明文字裡提到那些符號，不能影響判定（MealMate：只看一行裡有沒有「✗」，於是「✓」開頭、訊息裡提到 ✗ 的行被算成紅；改成只認以 ✗ 開頭的行，前一輪 8 條護欄突變的「抓到」全部作廢重驗）。這跟「不拿一樣東西的樣子判斷它屬於哪一類」是同一條原則，落到輸出解析上。
    - **「情境未成立」是獨立的結果類別**，跟「紅錯地方」意思相反、不得混在一起：**紅錯地方**＝情境成立、被擋下了，但擋它的是別條規則（對照組不夠精準）；**情境未成立**＝要測的狀況根本沒發生，這次什麼都沒量到。混在一起，就是把一次沒發生的測量記成一次測量。
      - 它**不算紅、不算通過、也不算數**：帳本不記成跑過，下一次選擇要再挑它；有專屬的回傳值與行首標記。
      - 判定依據取自**情境自己留下的痕跡**，不是執行器的推論（MealMate 的樣板是四個痕跡：壞檔還在、還原紀錄還在——這兩項證明中斷時 `finally` 沒跑——被殺的探針只有「開始」標記、沒有「結束」標記）。
      - 沒成立就換新的暫存環境重試，**有上限**（例：3 次），到上限硬失敗，不得靜默補一次。
      - **回報時成立與未成立分開數**：寫「成立 6、未成立 2（不算）」，不准寫「8 條都紅」。
      - **逾時與崩潰歸進這一類，不得被回傳值吃掉**：只看結束碼的判定器會把逾時當成「變紅＝被抓到」（StockDiary 實測：沒寫預期的突變只看結束碼，逾時被判成「✓ 變紅」；某支驗法的逾時設 15 分鐘、實測要跑約 55 分鐘，那兩條突變每次都逾時、每次都被記成被抓到，從來沒有證明過任何事）。逾時設定要大於那支的實測耗時。
      - 對照組：故意造一個必然不成立的情境（例：讓殺程序錯過時間窗、讓探針一啟動就結束、讓它逾時），必須判成「情境未成立」，不能判成紅、也不能判成綠。
    - **註解救不了一個不會擋的檢查**：知道一道檢查擋不住東西，就改掉或移除它，不要靠註解免責——標出疑點而不處置等於沒標，下一個人看的是輸出、不是註解。（MealMate 2026-10-02：寫程式時就發現「相加等於母體」是結構上必然的，在註解和回報裡都寫了，但沒改成會擋的檢查；Dispatch 讀的時候照樣把它當成檢查。見 §5.21。）
    - **通過的時候也要印出算過的東西**：實際紅了哪幾個、檢查了幾筆、對哪個版本查的。只在失敗時顯示計算過程的檢查器，通過時無法被稽核。那一行用**說明行格式**，判定符號不出現在行首——否則會被自己的行首判定誤判。「抓到 0 個」若是從「沒有出現任何報錯行」推出來的，要寫明。（StockDiary 2026-10-02：算不出「預期字串有沒有歧義」，根因是它的突變測試只在判錯時印出實際紅了哪幾個斷言，判對時不印。）
    - **「沒跑」不能寫成「全綠」**：照規則停下（例：被判成重負載、沒拿許可而回非 0）就是沒跑，回報寫「沒跑」與原因。（TripQuest 2026-10-02：`test:affected` 範圍放大成全套、又預測不出時間，被判成重負載、回了 8——沒跑；「照規則停下」很容易被寫成「一切正常」。）
    - 這一條是 §5.3（對照組）、§5.11（確認真的被執行到）、§5.13（失敗分支要有常設情境）換到「機制」這一層：不只是檢查，任何「條件成立才會走」的路——快取沿用、跳過、降級、重試、續跑——都一樣。
21. **母體與數字：數出來的才算，乘出來、減出來、從清單走出來的不算。**（2026-10-02 四個專案各自撞出來）
    - **「相加等於母體」可能是恆等式**：統計要從這一次實際產生的紀錄（log）逐行數，不要從清單走；印出紀錄那一側數到幾筆。結果類別分開數，**相加的和與應有的數字兩個一起印**。擋下並點名：同一條出現兩次以上、紀錄有而清單沒有、相加對不上、宣稱跑完卻還有沒輪到的。（一個專案回報「225 條突變：紅 225、沒紅 0、紅錯理由 0、沒有結果 0，相加 225」，而「相加等於 225」是 Dispatch 要求的母體檢查；後來查出那份統計是逐條走清單、缺結果的就補成「沒有結果」，所以相加永遠等於清單長度，不管實際跑了幾條。MealMate 和 TripQuest 查自己都中了同一個。）**驗收者提的檢查也可能是套套邏輯**——這次是驗收者自己要求了一個恆等式；提一道檢查之前，先問它在什麼情況下會失敗。
    - **母體數字不要乘出來，也不要減出來**：**數出來的和乘出來的兩個數字一起印**，不相等或是 0 就擋、不寫檔。（JLPT 的預期表原本印「共查了 1122 格」，那是 34 條 × 33 個情境乘出來的——乘出來的數字永遠對，就算一格都沒讀到。）推不出來、只能減出來的數字（「還沒跑 ＝ 母體 － 已跑」），在輸出裡寫明「那不是檢查」（TripQuest 的做法）。
    - **兩份空清單互比，會得到「差異 0」**：比對器先印出兩邊各有幾筆；對照組兩向放在同一支裡（故意改一筆必須比出 1 筆差異、自己比自己必須是 0 筆）。（TripQuest：比對器的行抽取規則抓不到任何東西，兩邊都是空清單，比出「差異 0 行」——完全吻合，不是接近；靠比對器自己的雙向對照組才發現。）「兩個不同的來源」要是**兩個不同的寫入者、不同的時間點**（例：驅動程式在跑時寫的進度，對上各工作自己留下的紀錄）；兩邊讀同一批檔案不算。
    - **兩次量測得出一模一樣的數字，通常不是一致，是共用了同一個來源**：每次開跑用獨立的紀錄檔（檔名帶上第幾次開跑）；看到兩次不同量測的數字完全相同，當成疑點去查。（MealMate：doctest 記憶體峰值印 653 MB，跟前一次開瀏覽器那次一模一樣；切段重算後它自己那一段只有 221 MB——五次抽樣全部寫進同一個紀錄檔，每次印的峰值都是累積的。）
    - 本節的檢查擋不住時照 §5.20「註解救不了一個不會擋的檢查」：改掉或移除，不靠註解。
22. **預期（突變的 `expect`、情境的預期表）：事前寫、不過期、不歧義。**（§5.9 的延伸；2026-10-02 四個專案各踩一次）
    - **預期清單也會過期，而它過期的樣子是「不如預期」**——很容易被讀成程式有問題，然後去修一個沒壞的東西。前置檢查：預期清單裡的每一項都要在當前的斷言集合裡存在，不存在就報「**預期清單過期**」，用獨立的訊息，不跟「不如預期」共用同一種結果。（TripQuest 三支：換 fixture 時預期還寫著舊檔名、漏列新加的斷言、要找的原文已不存在；MealMate、StockDiary、另一個專案也各中。）
    - **過期檢查擋不住「漏寫了後來新增的」**（JLPT 指出）。按母體大小選：母體小的（JLPT 33 個情境），**預期寫成對母體的完整劃分**——每一項都標「預期紅／預期不紅」、一格不缺，格數不等於母體就擋，新增項目時每一條都被迫回去表態；母體大的（MealMate 數百個斷言），**預期戳上母體版本**（寫這條預期時母體幾條、雜湊是什麼），母體變了而預期還戳著舊版本，報「**預期需要複審**」，用獨立訊息、**只報不擋**——擋住的話每次新增斷言都會讓整套停下，那條檢查很快會被關掉。
    - **預期字串要唯一對應一個斷言**：比對錨定在開頭或固定欄位，而且一段字只能對應到一個斷言；對應到 2 個以上就報「**預期有歧義**」並列出是哪幾個。（一個專案 165 條有預期理由的裡面 31 條有歧義——有一條的理由只寫「屬性」，而 11 個斷言名稱都含這兩個字，那 11 個裡任何一個紅了都算它被抓到；StockDiary 的 267 條全部是「失敗那一行的任何位置含這段字」。）更好的做法（JLPT）：**換掉比對的東西**——預期只用唯一編號、整組比對是否完全相同，並有檢查保證編號不重複；用結構保證，而不是用比對規則去避開。「靜態判斷不了」的**單獨列一類**，不併進「沒問題」（StockDiary 33 條樣板字串、MealMate 119 條，都單獨列）。
    - **預期事前寫，不要事後寫**：事後寫等於「發生什麼就成為預期」，那條檢查從此量不到任何東西。預期在跑之前寫定；無法事前寫的，依據欄標成「**事後**」，那幾條只能當下一次的基準，不能當成對預測能力的檢驗。（JLPT 的 29 條重跑，預期是幾個月前寫的而程式大改過；它 34 條裡 29 條標事前、5 條標事後。）
23. **環境與紀律。**（2026-10-02）
    - **裸寫的 `bash` 在 Windows 上可能被解成 WSL**：開跑前把要叫的指令解成完整路徑，落在系統目錄或 WindowsApps 底下一律拒絕，解不出來判「情境未成立」（§5.20）。（JLPT 的閘門驗法 2 秒就回 1、峰值 0 個程序——根本沒跑起來；MealMate 4 處、StockDiary 2 處、TripQuest 3 處都中。實測：從 PowerShell 的 PATH 解，第一支 bash 是系統目錄底下的那支、也就是 WSL；從 Git Bash 叫起來則正常。）先前的結果是否有效，取決於當時從哪裡叫的——**直接查正在跑的那支的執行檔路徑與父程序，不要靠推論**。
    - **不要用 `git add -A`（或 `git add .`、`git add <目錄>`）**，逐路徑 add：整個專案紀錄的可信度建立在「commit 訊息說的跟實際收進去的一致」。（TripQuest 用 `git add -A docs`，把共用慣例 v11.4 一起收進一個 commit，commit 訊息沒提到。）
    - **不要因為一個實測值「看起來不合理」就不採用**：丟掉一個實測值之前，先查出它為什麼是那個數字。丟掉實測值去用估值，比用一個看起來奇怪的實測值危險——估值沒有來源。有根據的排除不算（例：「那次量的時候某幾節還沒加進來」），要寫出根據。（MealMate 把 recipetest 的歷史紀錄「1 秒」判成「不像突變時的耗時，不採用」，實測是 1～2 秒，被丟掉的值是對的。）

## §6 文件

1. **`docs/STATUS.md` 是接手契約。** 最前面要有「目前進行中／交接」與「等 Yolin 回覆」這兩塊（叫什麼名字、是獨立一節還是小節，照本 App 現有的寫法）；這兩塊過期了就改寫，不要往下追加。只存在對話裡的決定、規則、踩坑，**每一輪結束前**寫進 STATUS——Session 可能在任何一輪突然斷，不一定走得到收尾。
2. 規格 `docs/SPEC_<主題>.md`；投票紀錄 `docs/VOTE_<日期>.md`。
3. 文件裡的數字盡量由靜態稽核從程式數出來比對；文件會漂移，而漂移不會讓任何測試變紅。
4. **總括句不能比逐格證據說得多**：寫「每一格都實測」，表內就不能有「未另做實驗」的格子。驗收照逐格證據，不照總括句。
5. **用腳本改文件，寫回之前先擋兩件**：行數只准變多（真的要刪就明講、明確放行）；原本的章節標題都要在。漏接後半份內容時，寫回去就把文件截掉了，而且不會有任何測試紅。

## §7 本檔怎麼改

1. **一條規則該進本檔還是留專案**，依序問：(a) 把規則裡的 App 名、檔名、數字換成另一個 App 的，還成立且措辭不必改嗎？(b) 在任何一個 App 違反它，Yolin 都會認為做錯了嗎？(c) 它是「原則＋某 App 的執行細節」嗎？——(a)(b) 都是 → 原則進本檔，細節留專案。領域紅線（健康、投資、使用者資料）永遠留專案；Yolin 指名「全部專案」的直接進本檔。
2. **只有統籌 Session 改主檔**：第一行版本 +1、日期改當天、§8 加一行。各 App 的副本由該 App 自己的 Session 依統籌者寫的工單更新。副本落後不擋任何工作。
3. 開發 Session 發現值得變成通則的規則：先照常寫進本 App 的 STATUS，並在回報裡標「候選通則」，由 Dispatch 轉給統籌者。不要改副本。
4. Yolin 明訂的直接進；Session 提議的要 Yolin 點頭；會改變四個 App 做法的才開 3 代理投票。
5. **條文新增或擴大一個檢查範圍時**，改主檔的人要同時：(a) 先拿新條文查自己的工具；(b) 用只落在新範圍裡的樣本，實測每個 App 現有的實作擋不擋得住，列出「誰還沒符合」寫進工單——不能從條文推論「應該已經有做」，也不能只靠各 App 做工單時碰巧發現；(c) 凡是「各 App 自行實作」的條目，條文裡要同時寫**怎麼證明這份實作真的會擋**（造什麼樣本、做什麼突變、預期哪一種報不符），不能只寫要做什麼。 (d) 工單的驗證條件要跟工單本文一致；寫工單的人照自己寫的驗證條件，把工單本身查一次。(e) 跨 repo 的盤點與驗收，先讀下 HEAD 雜湊，一律從那個雜湊讀（`git show <雜湊>:`，或 checkout 它的暫存複本），不讀工作區——對方的 Session 可能正在動工，工作區的數字與內容隨時在變。統計附上是哪個雜湊。
