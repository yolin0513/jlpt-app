## 3. 開發流程慣例

1. **規劃階段**：由共用的**統籌 Session** 理解 Yolin 的需求、拆解並寫成規格，規格檔放在本 App 的 `docs/`，命名為 `SPEC_<主題>.md`。模型與 effort 照共用慣例 §1。
2. **開發階段**：**開發 Session** 負責實作，也負責查找、蒐集資料；模型與 effort 照共用慣例 §1（統籌者在規格檔頭寫建議 effort，實際設定由 Yolin／Dispatch 決定，Session 不自行更換）。
3. **流程**：統籌者寫 spec → 開發 Session 實作＋查資料 → 回報並與需求（spec）逐項對照 → 與 Yolin 確認。
4. **較大改動或值得討論的議題**：由統籌者開 3 個代理投票（代理與統籌者同模型、同 effort，照共用慣例 §1）；各代理擔任統籌，把查資料的工作交給勘查代理，統籌者彙整投票結果後再回報。
   （判定清單見 §3.3；實作途中臨時遇到時由誰開票，見 §2 Q3。）
5. **禁止互動式提示框**：不得使用 AskUserQuestion 之類會跳出選單／多選題的互動工具。
   任何需要 Yolin 決定的問題，一律用**純文字**寫在回覆裡：清楚列出選項、附上自己的建議，
   然後停下等待，由 Dispatch 轉達給 Yolin、再把答案帶回來。
   **原因**：Yolin 常從手機或其他電腦遠端操作，互動式提示框只渲染在本機那台 PC，
   遠端點不到，Session 會就此卡住無法繼續。（同一個原因也讓權限提示、瀏覽器授權頁、GUI 登入視窗都成了陷阱，見 §8。）
6. **一律用繁體中文書寫**：所有「思考／判斷過程的文字敘述」與「回覆」都用繁體中文，
   讓 Yolin 能清楚跟上推理與取捨——包含說明為什麼這樣做、列出的選項與建議、
   進度回報、結論。程式碼、變數名、檔名、專有名詞、引用出處維持原樣，不必硬翻。
7. **測試紀律**：沿用 §4「測試紀律」既有慣例，不因分工調整而改變。

### 3.1 工作方式（Yolin 口頭交代過、之前沒寫進檔案的）

- **放手做、做完回報**：專案內的一般作業不要逐步請示（09-03 原話：「所有經過你判斷的操作都同意，不用問我了」）。
  **不要為了開會而開會**；修 bug、調樣式、補題庫、加測試、一般 commit／push 都直接做。
- **多項任務先列清單再做**：開工前把打算做的事列出來（涉及先前討論的內容，要引用原文，避免認知落差），送出後**不等回覆**直接開工。
- **段落式回報**：做完一個段落就回報一次，內容是「做了什麼、怎麼驗的、下一步」，不用等全部做完。
  題庫增補要分批，**每完成一級就 commit、push 並回報數量**。回報要**結論優先、簡潔**；需要轉達給 Yolin 的重點獨立標出。
- **修 bug 的標準做法**：在**線上版**重現、**查出根因（不要猜）**，修好後補一條「修正前會紅」的回歸斷言。
  回報固定三件事：**根因、為什麼既有測試沒抓到、補了哪些斷言**。
  「參數沒帶到」這類 bug 通常不只一個，**同類入口要全部驗一遍**。
  分不清是 bug 還是設計沒講清楚時，先**實際跑一次使用者流程**查清楚是哪一種。
- **UX 判準**：「**讓使用者搞不懂自己有沒有進步，本身就是 bug**」；「**按鈕不能按了沒反應**」。評估任何功能都用這兩條檢查。
- **版面標準**（09-03 定的）：新畫面要在 **360px 小手機**與**平板寬度**都沒有橫向捲動、平板限寬置中；**深色模式**文字對比達 WCAG AA（v1.3.0 已把級別色票調到 AA）。`verify-full` 已有 360px／平板溢出檢查，新畫面要加進它的檢查清單。
- **不要空轉**：會卡住等待的指令要背景執行；不要停在「等待中」就結束回合。只有真正需要 Yolin 決定的事才停下，並用純文字列選項。
- **被中斷後**：先回報 git 狀態（有沒有未 commit 的改動、是否與遠端同步）、中斷前在做什麼、線上版是否正常。
  完整且測過的改動可以直接 commit／push（Yolin 事後明講：「不需要為此保守」）；改到一半的先收尾成可運作狀態。
- **優先序自己判斷**，挑對使用者幫助最大、投資報酬率最高的幾項紮實做完，不必全做。
  新需求預設排在手上工作之後，**除非 Yolin 明說插隊**。
- **被權限提示擋住時不要停**：把需要的指令加進版控中的 `.claude/settings.json` 的 allow，再繼續；
  deny 清單裡的破壞性指令除外。每批回報註明「有無新增權限」。注意權限檔改了要有人在本機按一次「套用」才生效（§8）。
- **不主動截圖**（09-03 起）：除非 Yolin 要求，否則不產生截圖；功能驗證照做，用程式化方式（puppeteer 讀 DOM）。
  若 Yolin 要截圖：他那端讀不到 D 槽，要用可傳檔的方式（例如 SendUserFile）或問 Dispatch 目前讀得到的位置；
  截圖腳本的鏡像路徑一律讀環境變數 `MIRROR_DIR`，不寫死。
- **絕不代替 Yolin 輸入帳密**。需要他本人授權時（例如 GitHub 登入），走手機就能完成的 device flow：
  背景執行、拿到一次性代碼立刻回報、等他在手機輸入。要改走需要 token 的流程，先告訴他。
- **不接需要付費或金鑰的外部服務**（09-11 聽力時定的，適用所有功能）；評估後真的沒有其他路，先停下來問。
- **所有檔案都放在專案資料夾內**，不要污染磁碟根目錄；暫存檔、草稿放 Session 的 scratchpad。
- **跨專案唯讀**：同一層的其他 App（`../TripQuest`、`../StockDiary`、`../MealMate` 等）只能讀、不能改，
  也不要順手去對齊別的專案的文件。
- **功能或流程有變動就同步更新 README**（功能表、專案結構、份量表，不能只寫版本紀錄；§12 列了這條沒做好的後果）。
- **Session 收尾**（09-18 定的，之後每次交接都照做）：更新本檔開頭的「目前進行中／交接」；
  只存在對話裡的決定、否決方案、規則、失敗做法、坑都寫進來；逐條檢查過時內容；
  規劃中但沒動工的東西寫成 `docs/SPEC_<主題>.md`；收回所有背景任務與代理；`git status` 乾淨後 commit、push。

### 3.2 授權邊界（本 repo 內）

| 類別 | 做法 |
| --- | --- |
| 查詢、建檔、建資料夾、搬移檔案、安裝本機開發工具、改程式、補題庫、加測試、一般 git（commit／push／建分支）、部署到 Pages | **免問**，做完回報 |
| 刪除**尚未 commit** 的暫存檔 | **免問**（09-03 Yolin 明講的例外） |
| 刪除已 commit 的檔案或大量題庫條目 | **先確認**（Q2 待釐清：可能改為投票） |
| force push、`git reset --hard`、`git clean`、刪分支、改寫已推送的歷史 | **異動較大**，走投票；需要時由 Yolin 本人執行（見 Q2）。deny 只擋得住特定寫法，見表格下方 |
| 動到本專案以外的任何東西 | **不做**（跨專案唯讀）；專案外的非專案檔案（例如舊記憶檔）要先問 |
| 其他「異動較大」項目（§3.3） | 走投票 |

> **`.claude/settings.json` 的 deny 不是安全網**：它比對的是指令開頭，只擋得住這些確切寫法：`git push --force`／`-f`／`--force-with-lease`／`--delete`／`--mirror`、`git reset --hard`、`git clean -f／-d／-x`、`git branch -D`、`git filter-branch`、`git filter-repo`、`git update-ref -d`、`rm -rf`。
> 下列同類寫法**擋不到**，只能靠自律：`git push origin +main`（refspec 前加 `+` 就是強制推送）、`git -c … push --force`（本專案的 push 指令就是 `git -c` 開頭）、`git rebase`、對已推送 commit 的 `git commit --amend`、`git branch -d`、`del`／`rmdir`。要補進 deny，改完得有人在本機 PC 按一次「套用」（§8）。

### 3.3 「異動較大」的判定與投票

判定為異動較大（包含但不限於）：

1. 資料結構、JSON schema 或 IndexedDB 儲存格式變更（會影響使用者既有學習進度）
2. git 歷史改寫、force push、刪除分支
3. 大規模重構或跨多檔案的架構調整
4. 刪除檔案或大量題庫條目
5. 新增專案相依套件（加進 `package.json`）、變更部署設定或 Service Worker 快取策略
   （裝在電腦上的開發工具不算；App 本身沒有任何執行期相依）

**不算異動較大**：補題庫（只要新條目加在檔尾、不位移 id）、修 bug、調樣式、加測試。
新設定或小型紀錄**放進既有的 `meta` store**（例如模擬考成績 `examHistory`）也不算，因為不動 IndexedDB schema。

**投票規則**：3 個獨立代理各自分析影響範圍與風險，明確給 APPROVE 或 REJECT 加一句理由；多數決；票數分歧時採較保守的一方（2:1 算不算分歧，見 Q4）。
**投票結果本身就是決定**（Yolin 原話：「投票決定是否執行，最後把結果跟我說就好」），回報要包含：決議、三方立場摘要、實際做法、驗證結果、線上是否已更新。
主持者：09-03 起由開發 Session 自開 3 個 opus 代理；**09-14 起改由統籌者主持**（§3 第 4 條）。
**投票不能取代共用慣例 §2.1**（`docs/CONVENTIONS.md` v2）：就算投票通過，只要做下去有刪除或破壞使用者資料的風險（例如改 IndexedDB 儲存格式、做資料遷移），動手前仍然先問 Yolin（2026-09-19 統籌者裁定地板優先，Yolin 可否決）。

**投票紀錄**：
- **2026-09-03 v1.6.0 跨級別重複清理**：代理 1、3 APPROVE 方案 B；代理 2 REJECT 原提案「從來源檔刪行」並推薦 B+。
  也就是**三位都主張 B（載入時去重）**，不是三張 APPROVE 票。詳見 §7 第 1 條。

### 3.4 資安與隱私底線（repo 是 public）

GitHub Pages 免費方案不能用 private repo，所以 repo 一直是公開的。底線：

1. repo 與 git 歷史不得有金鑰、token、密碼、`gh` 憑證檔、`.env`、log 檔。
2. 不得有個人資訊：**真實 email**（git 作者一律用 GitHub noreply 隱碼信箱）、**本機 Windows 使用者名稱**、**本機 Claude 工作階段路徑與 UUID**。
   **寫任何文件（包括本檔、CLAUDE.md、SPEC）時也適用**：路徑一律用 `$HOME`、`~` 或「使用者家目錄」代稱。
3. 程式裡不留寫死的本機路徑，一律讀環境變數（例如 `MIRROR_DIR`）。
4. 前端不呼叫需要金鑰的外部 API；沒有第三方追蹤或分析；學習紀錄只存本機 IndexedDB，不送任何伺服器。
5. 不從 CDN 載入第三方腳本；字型用系統字型。

發現不該公開的東西：未 commit 的直接移除；已公開的要走改寫歷史流程（force push 屬異動較大）。
commit 前的常設自查（2026-09-23 改寫：原本「預期只命中本檔這一行」是拿本檔當對照組，而那一行只會被四個分支裡的兩個命中，
Windows 使用者資料夾與 gmail 兩個分支從來沒被對照過；共用慣例 v6 §5.3 要求對照組一定是合成樣本、跑同一個檢查）。三步照順序跑，同一個 `PAT`：

```bash
printf '%s\n' "C"":\\Us""ers\\x" "/c/us""ers/x" "local-agent""-mode" "a@gm""ail.com" | grep -c -i -E "$PAT"

```

## 4. 測試紀律

- **新斷言必須驗證會紅（mutation 驗證）**：拿修正前的程式碼（例如尚未部署修正的線上版，或暫時還原修正）跑一次，確認斷言確實失敗，才算有效。
  **回歸斷言要用使用者實際觸發 bug 的那個輸入**：v1.13.0 修正時順手把首頁 URL 的 `src=mix` 拿掉了，
  用新 URL 寫的斷言在舊版上竟然是綠的；補上使用者實際點到的舊 URL 後才會紅。
- **不寫假斷言**：不留永遠會過的斷言；**隨機出題的輸出不得綁死單一結果**
  （v1.9.0 讀音題 30% 是反向題，斷言寫死正向題文字，本機剛好連抽正向題沒露餡，線上才偶發失敗）。
- 測試若依賴某個設定（例如每日目標），要在該節自行明確設定，避免分節之間狀態污染（audit 各節在同一個瀏覽器 profile 連跑）。
- 有新行為就補斷言；修 bug 時要補一條「修正前會紅」的回歸斷言，並說明既有測試為何沒抓到。
- **README 宣稱的功能要有對應斷言**：羅馬字搜尋曾從第一版就壞掉（`romaji` 欄全空），因為沒有任何測試覆蓋。
- **不寫死題庫數量**：改驗「manifest 內部一致＋合理下限」，否則每次補題都誤報。
- **等畫面用 `waitForSelector`，不用固定 sleep**；檢查 SW 要先 `await navigator.serviceWorker.ready` 再輪詢 `reg.active`。
- **整套與上限**（共用慣例 §5.7 要求各 App 自訂；2026-09-21 定案）：本 App 的「整套」＝三支 puppeteer 腳本
  （`audit.mjs` 168 項／`verify-full.mjs` 30 項／`regress.mjs` 23 項，共 221 項），
  **實測約 290 秒（202s／62s／26s，2026-09-23 v1.16.0 在本機 `http://localhost:5173/` 量的，全綠；引用這個數字時要一起標時點）**。
  （同日稍早詞性篩選收尾後是 148＋30＋23＝201 項、179s／63s／25s。）
  （2026-09-21 v1.15.0 時是 135＋30＋23＝188 項、178s／63s／26s——多了 13 項，audit 耗時幾乎沒變。）
  **對線上跑會慢很多**：2026-09-21 對線上 v1.15.0 跑，verify-full＋regress 合計約 3 分鐘，audit 一支就跑了十幾分鐘（粗估，沒有精確計時；線上每個資源都要走網路）。
  **上限：每版都跑整套，不需要上限**——本 App 每批題庫增補與每次發版本來就三支全跑（§4.2、§5 第 5 步），
  三分多鐘的成本，追蹤「距上次幾版」比直接跑還貴。（2026-09-21 先裁示 5 版／20 條，同日依 v4 §5.7「上限照成本訂」改成這個寫法。）
  **共用慣例 v6 的兩條本 App 不適用**（2026-09-23 記）：§5.9「突變的 `expect`」——本 App 的突變是每條新斷言手動改壞驗紅，沒有突變清單、也沒有 `expect` 機制；§5.7 後半「耗時很久的整套，完整 log 寫到 repo 底下被 gitignore 的目錄（例如 `.logs/`）」——本 App 的整套是三支腳本、幾分鐘、每版都跑，不屬於耗時很久的整套。§5.7 前半「整套的日期、commit、範圍、條數、結果、耗時寫進 STATUS」本 App 本來就照做（見上面的實測數字與 §1「做到哪一步」）。將來若建了突變清單或出現耗時很久的整套，再照 v6 補。
  **適用但尚未觸發**（共用慣例 v8 §0.5，2026-09-24 記）：§5.10「加資料之前，先查畫面上依筆數寫死的上限」——本 App 會加資料（題庫增補），但這一輪沒有加；下次補題庫或加任何清單型資料時照做：先查學習頁、搜尋、錯題本、收藏、旅行情境等畫面有沒有「只列前 N 筆」，有的話加完要有一條斷言從畫面數得到新資料。
- **共用慣例 §5.7「平常只跑受影響的測試」是解除義務、不是設上限**（2026-09-19 Dispatch 轉達 Yolin 原話「請放寬，不用每一次小改動都全測，我會定期進行全面檢測」；v2 已寫進條文）。
  本 App 的三套測試流程（§4.2、§5 第 5 步）照舊，這條不是拿來減少測試的。

### 4.2 部署後的線上驗證流程

1. push 後，GitHub Pages 會排隊建置；遠端 main 已是新 commit 時，Pages 可能還在建前一版。
   輪詢 `sw.js` 的 VERSION 或 `gh api repos/yolin0513/jlpt-app/pages/builds/latest --jq '.status,.commit'`，
   等到 `built` 且 commit 相符，再多等約 10 秒。
2. 對線上跑三支：`audit.mjs <線上網址>`、`verify-full.mjs`（預設就是線上）、`regress.mjs <線上網址>index.html`。
3. 三支一起跑會超過 Bash 工具 120 秒的前景上限，要用背景執行、等完成通知。

### 4.3 目前的驗證狀態與交接時發現的測試問題（2026-09-18）

- **App 本身沒問題**：對線上 v1.13.0 用全新瀏覽器 profile 連開 6 輪，JLPT 測驗、旅行測驗、搜尋三個畫面**每次都正確渲染，console 零錯誤**。
- **發現一：過去幾版的 verify-full 沒測到本機改動**。`verify-full.mjs` 不帶參數測的是線上（§4.1），
  所以 v1.10.0～v1.13.0 期間「push 前 verify-full 30/30」測的其實都是線上舊版；v1.13.0 部署後也沒再對線上跑 verify-full、regress。
- **發現二：verify-full、regress 在線上會頻繁偶發失敗**。交接時補跑，修正前 verify-full 4 輪有 3 輪失敗、regress 3 輪有 2 輪失敗
  （失敗項集中在：測驗「0 題」、旅行測驗沒有選項、收合 toggle、搜尋頁載入）。
  - **根因是測試的時序競態**，不是 App 的 bug：各腳本的 `go()` 只在網路閒置後固定等 0.5–0.6 秒，
    但線上冷快取時，畫面要在網路閒置後**再 1–2 秒**才渲染完（實測 JLPT 測驗 1.4–4.8 秒、搜尋 2.2–3.4 秒）。
    後面直接操作 DOM 的檢查就會撲空，有一段甚至對 `null` 呼叫 `click()`，讓整支 verify-full 中斷、連總結都沒印出來。
  - toggle 那項另有一個問題：它用「清單高度 > 0」判斷有沒有展開，但點開後場景清單要等資料載入才有內容，網路慢時清單已顯示卻還是空的。
- **修正**（只改測試，不動 App、不放寬任何判斷）：
  - `audit.mjs`、`verify-full.mjs`、`regress.mjs` 的 `go()` 改成**等 `#view` 真的有內容才回傳**
    （路由只在畫面資料全部備妥後才一次放進 `#view`，中間沒有佔位元素，所以這等於「渲染完成」）。畫面 15 秒內沒出來，後面的檢查照樣會失敗。
  - toggle 改看 CSS `display` 判斷有沒有展開。**mutation 驗證**：把 v1.2.1 的 bug（`.chips` 的 `display:flex` 蓋掉 `[hidden]`）注入頁面後，
    這項從 `[false,true,false,true]` 變成 `[true,true,true,true]`，確實會紅。
- **修正後的線上結果**：verify-full 連跑 3 輪都是 **30/30**、regress 連跑 3 輪都是 **23/23**、audit **97/97**（都對線上 v1.13.0，2026-09-18）。
  這些結果只證明測試穩定了；**App 在真機上的行為仍未驗證**（見 `SPEC_device_test.md`）。

## 5. 資料慣例

- **題庫新條目一律附加在 `data/src/*.txt` 檔尾**。id 依**有效資料列**的順序編號（`n5-v-0001`…），是使用者 IndexedDB 裡進度的 key。
  `build_data.py` 只替通過檢查的資料列編號：**空行、`#` 註解、被略過的壞行都不算**（壞行＝欄位不足、第 1 或第 3 欄空白、含西里爾字母）。
  所以在中間插入或刪除資料列、或把某一行改壞，都會讓後面的 id 位移；在中間插入註解或空行則不會。**規模很驚人**：當年若刪 27 行，會讓 2432 筆裡 918 筆（37.7%）的 id 指向別的詞，
  而且錯位完全靜默（詳見 §7 第 1 條、附錄 A）。
- 修改既有條目只能**就地改那一行的欄位**。**「總行數不變」不夠**：某一行若被改壞（欄位空掉、混入西里爾字母）而被 build 略過，行數不變但後面的 id 全部位移。
  正確的檢查是 rebuild 後**逐筆比對既有 id 的內容**：拿 `git show HEAD:data/grammar/n2.json` 與新產生的 `data/grammar/n2.json` 逐筆比對 id→句型（單字比 id→漢字｜假名），全部相同、且各級 count 只增不減（v1.10.0 就是這樣驗的）。
- 改完跑 `python scripts/build_data.py` 與 `python scripts/check_data.py`。
- **跨級別重複**用 `data/src/dedup.txt` 在載入時隱藏（格式：`級別 | v或g | 漢字或句型 | 假名`），不從來源檔刪行；
  從 `dedup.txt` 刪掉那一行就能還原。build 會驗證每條規則在該級恰好命中 1 筆、較低級別找得到保留筆，否則直接報錯。
  - **判定重複的標準**（Yolin 定的）：同漢字＋同假名（文法為同句型）**且同義**才算；同形不同義、不同詞性用法可能本來就該分級收錄，不要誤刪。
  - **隱藏前先把較高級別那筆獨有的義項、詞性併進保留的那筆**（v1.6.0 只合併了 3 筆，還有 3 筆沒做，見 §11 第 1 項）。
  - 讓 `check_data` 的跨級重複警告保持 0：常駐的警告會讓人麻痺，新出現的重複（例如「慌ただしい」）一定要收進 `dedup.txt`，讓「有警告」重新代表「有新狀況」。
- 題庫數字有兩套：`count`（含隱藏）與 `activeCount`（實際可練）。寫文件或回報時要註明用哪一套；**建議一律用 activeCount**。
- **選詞原則**：以歷屆 JLPT 出題頻率為優先，參考公開高頻詞表、舊制 4／3／2 級出題基準、常見必考句型；
  **不為湊數加冷僻詞**；上網查資料要用可信的日語教學或檢定來源。五級份量要拉齊、對得起實際考試範圍（audit 有「五級份量均衡」斷言：任一級低於最多那級 70% 即失敗）。
- **正確性第一**（Yolin：「寧可慢一點也不要出錯」）：假名、詞性、釋義、例句都要正確自然，例句難度符合該級；
  生活旅行的漢字差異，日文語義與讀音尤其要準。
- **每批增補的標準流程**：
  1. 寫草稿（放 scratchpad，不放專案內）。
  2. **同一輪所有草稿一次過濾**：`node scripts/filter_vocab_draft.mjs <草稿們>` 或 `node scripts/filter_grammar_draft.mjs <草稿們>`。
     會比對五級全部既有條目與同輪其他草稿、驗 7 個欄位、擋生成雜訊。
  3. 附加到 `data/src/` 對應檔的檔尾 → `build_data.py` → `check_data.py`。（兩支從 2026-09-24 起遇到缺檔或空的一組都會停；改過這兩支本身，要跑 `python scripts/test_datacheck.py`。）
  4. **人工抽樣至少 40 條**（09-03 定的門檻；v1.7.x 之後幾批低於這個數，見 §11）。另做「例句假名必須是例句中假名的超序列」檢查，抓漏字與多字。
  5. 跑測試 → commit、push → 等 Pages 建好 → 線上驗證。
- **波浪號一律用全形 `～`（U+FF5E）**，不是長得一樣的 `〜`（U+301C）；寫檢查用的 regex 要兩種都列。
- 例句**避免讀音有歧義的專有名詞**（台北有 タイペイ／たいほく 兩種讀法，已改成東京）；
  例句同時供朗讀、填空、假名比對使用，讀音不唯一就會出錯題。
- 純假名的文法句型（如 `～ながら`、`～も`）讀音欄**刻意留空**。
- 合法例外，不要當錯誤去「修」：例句自然含 CD、SNS（假名欄拼成 シーディー、エスエヌエス）；
  `～得る／～得ない` 讀音含全形斜線；顧みる／省みる 同音不同詞，要分開保留。

## 6. 關鍵決定與理由

> 已寫在 README 版本紀錄的，這裡只列結論與「為什麼」；README 沒寫理由、或只存在對話裡的，這裡寫完整。

### 架構與部署
- **原生 JS ES Modules＋IndexedDB＋Service Worker，無框架、無打包**：開檔就能改、門檻低；日後只要改純文字題庫、跑一行指令就能增補。Yolin 每次派工都重申這條。
- **題庫用 pipe 分隔純文字＋build 產生 JSON、id 依行序**：方便人編輯。代價是 id 會因插入／刪行位移，這個限制是後來所有資料決策的根源。
- **自己寫多執行緒 `scripts/serve.py`**：Python 內建單執行緒 `http.server` 在 Windows 遇到並發請求會出 `net::ERR_NO_BUFFER_SPACE`（當時同時在 `data.js` 加了 `fetchRetry` 重試 3 次）。
- **Pages 從 main 根目錄部署，不用 Actions；全部資源用相對路徑**：Pages 專案站在 `/jlpt-app/` 子路徑下，資源、fetch、SW scope 都要能在子路徑運作。
- **文字檔換行統一 LF**：`.gitattributes` 設 `* text=auto eol=lf`；`build_data.py` 所有 `write_text` 都帶 `newline='\n'`。
- **全域 CSS `[hidden]{display:none!important}`**：有 `display:flex` 的 class 會蓋掉瀏覽器預設的 `[hidden]`，這一條讓以後所有用 `hidden` 做展開收合的元件都正常，**不要刪**。
- **返回鍵永遠不會退出 App**：`history` 有增加才 `history.back()`，否則依對照表導到上一層（冷啟動或深層連結進來時沒有上一頁）。
- **路由加 dispatch 世代碼**：快速切頁時，晚到的舊畫面會蓋掉新畫面；只有最新一次 dispatch 能渲染。新增畫面都要經過這套，不要直接改 `#view`。
- **首屏效能**：各畫面動態 `import()` 延遲載入＋首屏模組 `modulepreload`（JS 96KB→32KB、首屏內容 3.6s→1.2s）；SW 安裝時只快取外殼，題庫在首屏後 1.5 秒用 `WARM_DATA` 背景暖機。
- **觸控裝置自動隱藏鍵盤快捷鍵提示**：手機是主要情境，提示只會佔版面。改 `keys.js` 或提示 UI 時要保留這個判斷。
- **權限白名單寫進版控的 `.claude/settings.json`**：Yolin 原本要寫進 `settings.local.json`，但那個檔被 gitignore，所以改寫進版控檔；破壞性指令刻意放進 deny。

### 資料與快取
- **跨級重複採「載入時去重」（B+）**：理由見 §7 第 1 條。
- **`loadSet` 過濾隱藏題，另設 `loadSetRaw` 給 `findItem`**（v1.6.1）：隱藏不等於刪除，使用者在隱藏 id 上的進度、錯題、最愛仍要解析得到，否則會變孤兒紀錄。
- **題庫快取自動失效**（v1.7.0）：`dataVersion`（全題庫 SHA-1 前 12 碼）存成 SW 的快取標記，不符就整批清掉重抓；`manifest.json` 改 network-first。起因是 v1.5.0 時忘了升 SW 版號，使用者拿不到新題庫。
- **匯入改「取代」語意、備份升 v3 帶 `idScheme`**（v1.7.0）：合併語意會把新舊資料混在一起；將來若重編 id，沒有 id 方案欄位的舊備份會把錯的 id 靜默灌回來。
- **題庫載入用 `once()` 快取進行中的 Promise**：搜尋頁多張卡同時載入時，manifest 被同時抓了 5 次（cache stampede）。**新增任何載入函式都要走 `once()`**。
- **搜尋改用精簡索引 `search-index.json`**：例句三欄佔題庫 57% 體積而搜尋用不到；13 個檔 gzip 192KB → 1 個檔 75KB。保留可讀的欄位名，不改短 key（gzip 後只省十幾 KB）。
- **模擬考成績存 `meta.examHistory`，不新增 store**：不動 schema，就不算異動較大。

### 學習機制
- **SRS 用 Leitner box 0–6、`LEARNED_BOX = 3`**：答對 +1 盒、勉強 −1 盒、答錯歸 0。門檻為什麼選 3，對話中沒有說明。
- **smart 排程改成到期題優先，最多佔一輪七成**（v1.13.0，`DUE_QUOTA = 0.7`）：原本新題優先，題庫三千多條讓到期題永遠排不進來。保留三成給新題，免得複習債一多就看不到新內容。0.7 這個數字沒有更精確的依據。
- **畫面顯示「學習中」、直接寫出「答對 3 次、最快跨 3 天」**（v1.13.0）：只顯示已掌握的話，第一天看到的永遠是 0，使用者會以為壞掉。
- **聽力用瀏覽器內建 `speechSynthesis`**：零成本、免金鑰、本機語音可離線，符合無後端定位；本機 Windows 實測有 4 個日文語音。

  出題比例 70% 漢字→讀音、30% 讀音→漢字，對應 JLPT 文字語彙第 1 大題「漢字読み」與第 2 大題「表記」。
- **例句填空以「空格後接字相同 +4」為主訊號**：第一版只看同詞性，做出一眼就錯的選項（見 §7）。
- **模擬考作答當下不給對錯、時間照真實 JLPT 節奏、未作答不寫 SRS、不含讀解並在畫面講明**（v1.11.0）：詳見 README v1.11.0。
- **熱力圖深淺對照每日目標、範圍 12～53 週伸縮**（v1.12.0）；**弱點清單權重 .55／.30／.15**（v1.12.0），權重數值本身是經驗值。

## 8. 踩過的坑與環境限制

### 環境限制
- **記憶檔跟著工作目錄走**：開發 Session 前期的工作目錄是磁碟根目錄，三份記憶檔存在那個目錄對應的記憶區；09-14 起工作目錄改成本專案，對應的記憶區是空的。**只寫在記憶檔的規則，新 Session 等於沒有**——這就是本檔要寫這麼完整的原因。
- **Yolin 常只有手機或遠端電腦，本機 PC 上的任何提示都按不到**：權限提示、互動式提示框、瀏覽器授權頁、GUI 登入視窗都會讓 Session 卡死。改用手機就能完成的方式（例如 device flow）。
- **改了 `.claude/settings.json` 的權限，要有人在本機 PC 按一次「套用此專案的權限設定」才生效**。Yolin 不在電腦前時新規則不會生效；他回到電腦前時，Dispatch 會通知，請 Session 立刻觸發一次權限提示讓他按。
- **Dispatch 讀不到 D 槽**：要交給 Yolin 的檔案不能只回報 D 槽路徑。
- **Dispatch 轉達的數字可能過時**（例如轉達「題庫 3307 條」時實際已是 3517）：回報與判斷前一律用 manifest、git 實查。
- **gh CLI**：用官方 zip 解壓在使用者 Temp 目錄底下的 `gh-cli/bin/gh.exe`（**Temp 目錄可能被系統清掉**，被清掉就重新下載同版 zip；登入憑證在 `~/.config/gh`，不受影響）。
  **每次呼叫 gh 都要帶 `GH_CONFIG_DIR="$HOME/.config/gh"`**，否則會顯示未登入（Windows 版 gh 預設讀另一個目錄）。
  帳號改名後 `gh auth status` 仍顯示舊名，確認身分用 `gh api user --jq .login`。現有 token 沒有 `delete_repo` 權限。
- **git push 會無聲卡死**（Git Credential Manager 在等看不到的 GUI）。一律用 `CLAUDE.md` 裡的 push 指令（gh credential helper＋`GIT_TERMINAL_PROMPT=0`＋`timeout 90`）。
- **Windows 主控台是 cp950**：Python 印中日文會報錯或亂碼。`build_data.py`、`check_data.py` 已設 UTF-8；臨時腳本用 `io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8')`。**看到亂碼先用程式讀檔確認，不要直接認定檔案壞了**。
- **Bash 工具是 Git Bash**：
  - 沒有 `pkill`（`.claude/settings.json` 放行的 `pkill` 規則形同虛設）。關本機伺服器用 PowerShell：
    `powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 5173 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }"`（這條目前不在 allow 清單，見 §12）。
  - 不認得 PowerShell 語法（例如 `2>$null` 會讓整串 `&&` 中斷）。
  - `grep -P` 不能用、Unicode 範圍的 grep 會誤判；找非日文字元用 Grep 工具或 Python／Node 的 regex。
  - **每次指令的工作目錄可能被重設**，指令開頭先 `cd` 到本 repo 的根目錄，或用絕對路徑（文件裡不要寫出本機的完整路徑）。
  - 超過 120 秒的指令會被移到背景；前景 `sleep` 會被擋。

### 資料與工具的坑
- **Git Bash 的 `sed -i` 會把含 `|` 的題庫檔整個清空**：GNU sed 把 `\|` 當成「或」，每一行都匹配而被刪光（09-03 曾把 `vocab.n3.txt` 清成 0 行）。**題庫檔一律用 Python 或 Edit 工具改**，並在 rebuild 後逐筆比對既有 id 的內容沒變（§5）。
- **sed 取代字串裡的 `\n` 會變成真的換行**（曾把 `build_data.py` 改成語法錯誤）：含反斜線跳脫的程式碼不要用 sed。
- **Edit 工具比對含 `\uXXXX` 跳脫的程式碼常失敗**：先照抄原文；還不行就整檔重寫。
- **bash heredoc 夾帶大段含引號／反引號的內容會解析失敗**：先用 Write 寫成檔，再用 python 執行。改中文文件用 python 以 `encoding='utf-8'`、`newline='\n'` 讀寫。
- **Claude 產的題庫草稿一定會混入雜訊**：西里爾字母、韓文、英文單字，連欄位內都有（例如「明日、три時に」「さほど difficult」）。只檢查欄位數擋不住，要用過濾腳本加人工看一遍。
- **`check_data.py` 不驗文法的讀音欄，也不驗例句假名是不是純假名**：這些欄位打錯字抓不到（§12）。
- **Windows 產檔會有 CRLF 警告**：`.gitattributes` 已處理，只是雜訊。rebuild 後 `git status` 可能顯示 JSON 已修改但 `git diff` 是空的，`git checkout data/` 還原即可，不要誤 commit。
- **`git add` 的萬用字元碰到被 gitignore 的檔會整批失敗**：改列確切檔名或用 `git add -A`。
- **殘留的 `.git/index.lock`**：2026-09-18 交接時 `git add` 失敗，因為 repo 裡有一個 20:25 建立的空鎖檔（早於交接開始，

  - **「實測擋得下」要用實際推送的那一整行來驗**，不是只驗自查腳本回傳幾（統籌者 2026-09-23 補進共用慣例主檔的說法）。管線的回傳值是最後一個指令的，要分開看兩件事：
    1. **自查的失敗有沒有被吞**：本 App 當時那一行是 `commit && 自查 && 推送 2>&1 | tail -1`。bash 裡管線比 `&&` 綁得緊，等於 `commit && 自查 && (推送 | tail -1)`，自查失敗會讓 `&&` 直接短路、推送根本不會開始——**這一半沒有被吞**。實測：兩次被擋的都是整行跑的，輸出裡沒有推送成功的那行、遠端 HEAD 沒動。
    2. **推送本身的失敗有沒有被吞**：`推送 2>&1 | tail -1` 的回傳值是 `tail` 的 0，推送失敗也看起來成功——**這一半有被吞**，當時只靠每次印出的遠端與本機 HEAD 讓人眼比對。2026-09-23 在拋棄式的本地假遠端上實測：推送失敗時舊寫法回 0，加 `set -o pipefail` 回 128。TripQuest 撞到的就是這一半：推送失敗被吞，後面的線上確認對著舊版驗、看起來還是綠的。

### 程式的坑
- **新增 JS 檔一定要加進 `sw.js` 的 `SHELL_ASSETS`**：延遲載入的畫面若線上時沒點過就不會被快取，離線時該頁會壞。
- **部署後使用者要「再開一次」App 才會跑到新程式**：外殼是 stale-while-revalidate，第一次開啟仍用快取的舊 JS。請 Yolin 驗證修正時要提醒「完全關掉 App 再開，必要時兩次」。
- **版本字串分散三處手動更新，已經漂移**：README 版本紀錄、`sw.js` 的 `VERSION`、統計頁頁尾（`js/views/stats.js`，**目前還寫 v1.9.0**）。發版時三處一起改（§11 第 1 項）。
- **`data.js` 的 `normalize()` 是白名單**：題庫 JSON 加新欄位要同步改 normalize，否則前端看不到（v1.6.0 加 `dup` 時就踩過）。
- **`bindKeys` 只在畫面根節點脫離 DOM 時自動解除**：在同一個 wrap 內重跑流程（例如模擬考「再考一次」）會重複綁定。
- **焦點在按鈕上時按 Enter 會雙重觸發**（原生 click＋全域 keydown），曾造成跳題；非同步的評分函式要加重入旗標。
- **不要用按鈕的顯示文字判斷答案對錯**：選項加了編號 span 後 `textContent` 就對不上。
- **百分比高度的圖，父層要有明確高度**，否則全是 0。
- **用閉包狀態＋`setTimeout` 驅動的畫面**：狀態改變要同步到 DOM；收尾時要清掉殘留 timer（聽力頁踩過兩個）。
- **測試用瀏覽器會拿到舊模組、舊 CSS**：驗證前 hard reload 或換新的 puppeteer profile；主題只在啟動時讀一次，改設定要整頁重載。
- **puppeteer 只改 hash 的 `page.goto` 不會重新載入**：一律先 `goto('about:blank')`；固定的 `userDataDir` 會被鎖住，每次用新的。
- **puppeteer 用滑鼠點畫面下緣的按鈕，會點到固定的底部導覽列**（2026-09-23：點「四選一測驗」結果跑去「複習」）。puppeteer 的捲動只保證元素進入視窗、不保證沒被蓋住；audit 第 [22] 段的 `clickButton` 先 `scrollIntoView({ block: 'center' })` 再點。
- **預覽瀏覽器的 `console.clear()` 清不掉工具緩衝**；`indexedDB.deleteDatabase` 在連線還開著時會卡住；用 JS 寫入 IndexedDB 後立刻換頁，畫面可能在交易提交前就渲染。
- **漢語詞的中↔日題幾乎白送**（例如 状況≈狀況）：這是中日共用漢字的本質，**刻意不處理**；要改善可改出讀音題或填空題。

- **路由**（`js/app.js`，hash 路由，畫面用動態 `import()` 延遲載入）：

  store：`progress`（key `itemId`，有 `due` 索引）、`mistakes`（`itemId`）、`daily`（`date`）、`meta`（`k`）、`favorites`（`itemId`）。

- **Service Worker**（`sw.js`）：外殼 stale-while-revalidate；題庫 cache-first；`manifest.json` network-first。
  `dataVersion` 存成快取標記 `__data_version__`，不符就整批清掉重抓 → **只改題庫不必升 VERSION**；
  改了 JS／CSS 外殼才要升 `VERSION`，新 JS 檔要加進 `SHELL_ASSETS`。
- **版號**：v1.14.0 起三處對齊——README 版本紀錄、`sw.js` 的 `VERSION`（目前 `jlpt-v1.15.0`）、統計頁頁尾都是同一個號碼，發版時一起改；
  `package.json` 的 `version` 一直是 `1.0.0`，沒有在用。
- **備份格式**：`EXPORT_VERSION = 3`，帶 `idScheme: 'positional-v1'` 與 `dataVersion`；匯入是「取代」（先清空再寫入），仍接受 v1、v2 舊備份（它們沒有 idScheme）。

## 附錄 A：萬一將來真的要重編 id

目前採「載入時去重」，**不需要**重編 id。這一節留給將來題庫大改版、真的非重編不可的時候——
2026-09-03 三位投票代理判定這件事「可以做對，但缺一不可」，以下是他們開出的條件：

1. **對照表在 build 期內嵌成靜態常數**（新舊 id → 內容簽章），遷移過程完全不 fetch，避開 SW 快取競態。
   **對照快照必須在任何一次 rebuild 之前產生**；只要有人先跑了 `build_data.py`，快照就會無聲失效。
   對照鍵只用 (level, kind, kanji, kana)，文法用 (level, g, pattern, reading)；**不要用 meaning 或 pos**（有 13 組本來就不同）。
2. **保留那一筆自己的 id 也會跟著位移**（例如 n2-v-0143 刪行後會變成 n2-v-0138），重導向表要用刪行後重新產生的 id。
3. **觸發條件看實際抓回的 `manifest.json` 裡的 `idScheme`**，不看 meta 旗標；旗標要記版本字串，不能用 boolean。每一筆 row 都要有冪等標記。
4. **開機流程要先 await 遷移完成**，才讓任何畫面讀進度（目前 `app.js` 的 `initTheme` 是 fire-and-forget）。
5. **`db.js` 要先支援跨 store 的原子交易**（目前 `tx()` 只收單一 store）。
6. **雙胞胎合併規則要與寫入順序無關**：progress 的 box 取 max，reps／correct／wrong／lapses 相加，updated 取 max，due 取 min（代理意見分歧：也有人主張取 max 較保守）；
   mistakes 的 count 相加、lastWrong 取 max、resolved 取 AND；favorites 的 added 取 min。
7. **遷移前強制 `exportAll` 下載備份**，UI 讓使用者確認「已存檔」才繼續；每台裝置各存一份。
8. **先離線 dry-run**：在 `scripts/` 用 Node 拿使用者真實匯出的 JSON 跑一次，印出「幾筆位移、幾筆合併、幾筆變孤兒」，給本人看過才執行。
9. **不變量斷言**：`sum(reps)`、`sum(correct)`、`sum(wrong)` 前後必須完全相等；對**全部**舊 row 逐筆比對簽章，不抽樣。
10. **同時升 `idScheme`，並提供舊備份轉換**；`resetAll` 不清 meta，重置後再匯入舊備份的路徑也要擋。
11. 這件事屬**異動較大**，要投票。
