```bash
# 在本 repo 根目錄執行；只動暫存目錄
T=$(mktemp -d); git init -q --bare "$T/remote.git"
git clone -q --no-local . "$T/work" && cd "$T/work"
git remote set-url origin "$T/remote.git" && git push -q origin main
# 看假遠端現在是哪個 commit：git --git-dir="$T/remote.git" rev-parse main

# 「推送被拒」：pre-receive 回傳 1。做一個乾淨的 commit，跑你的推送那一整行 → 必須停在推送那一關
printf '#!/bin/sh\nexit 1\n' > "$T/remote.git/hooks/pre-receive"; chmod +x "$T/remote.git/hooks/pre-receive"
rm "$T/remote.git/hooks/pre-receive"   # 驗完拿掉

# 「推送回報成功、遠端卻沒更新」：post-receive 把 main 退回舊值 → 推送會回報成功，但比對遠端那一關必須停下
printf '#!/bin/sh\nwhile read old new ref; do [ "$ref" = refs/heads/main ] && git update-ref refs/heads/main "$old"; done\n' > "$T/remote.git/hooks/post-receive"; chmod +x "$T/remote.git/hooks/post-receive"
rm "$T/remote.git/hooks/post-receive"   # 驗完拿掉
```

至少驗這五種，每一種都記下回傳值、假遠端有沒有被動到：
1. 要推的檔有命中（在暫存複本裡 commit 一個當場組出來的合成樣本）→ 停在自查、假遠端沒動。
2. 自查的對照組弄壞 → 停在自查、假遠端沒動。
3. 推送被拒（`pre-receive`）→ 停在推送，後面的確認沒跑。
4. 推送回報成功、遠端卻沒更新（`post-receive`）→ 停在比對遠端。
5. 全部正常 → 推上去、假遠端＝本機。你的閘門若推送後還會讀線上網站，這一種不必驗線上那一步。

驗法最好也寫成 repo 裡的腳本，改過閘門就重跑。

   - **推送本身**：失敗就停。不要接著做線上確認或整套檢查——那會對著沒推上去的舊版去驗，看起來還是綠的。
   - **推送後**：比對遠端的 HEAD 等於本機，才算推上去；這一道堵住「推了但沒成功」。

   **不要用管線包任何一步**（例如為了截短輸出加 `| tail -1`）：管線的回傳值是最後一個指令的，前面那一步的失敗會被吞掉，`&&` 照樣往下走，不報錯、沒有任何徵兆，只會在真的該擋的那一次默默放行。要看輸出就導到檔案再看，或在同一個 shell 先 `set -o pipefail`。

   **要用實際推送的那一整行實測，而且分別製造每一關的失敗**，不能只驗第一關：自查——餵一個一定會命中的合成樣本（放在自查會掃到的地方）；推送——讓推送失敗；推送後——讓遠端與本機對不上。製造失敗而不碰 GitHub 的做法：在暫存目錄建一個 bare repo 當測試遠端，放一個回傳 1 的 `pre-receive` hook 就是「推送被拒」，放一個把 main 退回舊值的 `post-receive` hook 就是「推送回報成功、遠端卻沒更新」。會擋的情境用 `--dry-run` 或這種本機測試遠端當保險，就算閘門沒擋住也只是試推、不會公開；用過真的遠端當測試，測試分支驗完就刪，再用 `git ls-remote` 確認遠端從來沒出現過它。每一關失敗用不同的回傳值（例如自查 1、推送 2、遠端與本機對不上 3），一看就知道是哪一關。

   **閘門腳本放在 repo 裡，不放 session 的暫存區。** session 會被刪、會撞額度、會被換掉；閘門跟著消失，就有一段沒有防線的空窗，新 session 重建時還可能重犯同樣的錯。**規則進 repo、資料不進 repo**：不能公開的內容（例如個資黑名單）從被 `.gitignore` 擋掉的檔案讀進來，並在 STATUS 寫明新 session 怎麼取得那個檔——否則搬進 repo 之後，新 session 照樣卡住。`CLAUDE.md` 若寫了推送指令，要指向閘門，不要留一條繞過閘門的「一律用這條」。改過閘門就把「分別製造每一關的失敗」那組驗法重跑一次；驗法最好也寫成 repo 裡的腳本。

   （2026-09-23 查了四個 Session 的推送那一行，沒有一個是乾淨的：三個在自查後面接了 `| tail -1`，自查失敗被吞掉，其中一次一個 commit 帶著自查命中被推上去；另一個的自查是好的，但在推送後面接了 `| tail -1`，推送失敗時，後面的線上確認照樣對著舊版跑。幾次都剛好沒有個資。）

## §3 溝通

1. **禁止互動式提示框／多選題工具（`AskUserQuestion` 之類）。**（Yolin 2026-09-16 明訂）需要 Yolin 決定的事一律用**純文字**寫在回覆裡：列出選項、每個選項的代價、你的建議與理由，然後**停下來等**，由 Dispatch 轉達。理由：Yolin 常從手機或另一台電腦遠端操作，提示框只渲染在本機那台 PC，遠端點不到，Session 就此卡死。

3. **回報分開寫「實測驗證過的」與「推論的」。** 結尾放需要 Yolin 決定的事項，沒有就明講沒有。

## §4 給使用者看的文案要誠實

拿不到、算不出、還沒開放的，就照實寫（「尚未取得」「未估算」「這一版尚未開放」這類話）——不顯示 0、不用預設值冒充使用者輸入、不用舊資料冒充新資料。

## §5 測試紀律

1. **每條新斷言都要證明它會紅**：把對應邏輯改壞（突變），或拿修正前的程式跑，測試必須失敗；修回去必須綠。修 bug 時補一條「修正前會紅」的回歸斷言，並說明既有測試為什麼沒抓到。有新行為就補斷言。
2. **不寫假斷言。** 抓到過的形狀：母體是空的；母體恰好是「有問題的那幾個」；等待條件在上一頁就已經成立；反例太弱、被別條規則順便擋掉；掃描器把註解當程式碼；「應該是 0」旁邊沒有「母體非空」。寫完一條 `noneOf`／`everyOf` 就問一次：**這個母體現在有幾個元素？** 註解不是斷言。
3. **檢查器要有對照組**：餵已知該被抓到的輸入，斷言真的抓到。**斷言驗語意、不貼字面。** 對照組**一定要有**自己造的合成樣本，而且跑的是同一個檢查（同一個搜尋式、同一段程式）；真實資料可以當第二道對照，不能單獨當對照組——它會隨時間變（實例：公開前自查的 email 對照組用 git 歷史的作者信箱，改用 noreply 之後就被排除規則濾掉、命中 0；路徑類的對照組去搜本 App 的 `CLAUDE.md`，那些路徑清掉之後，目標與對照組都是 0 命中，自查看起來正常、其實早就失效；「預期只命中本檔這一行」這種寫法，本檔那一行只碰得到其中幾個分支，其餘分支壞了也看不出來）。**每一類、每一個分支都要有自己的合成樣本。**
4. **從使用者實際會走的入口測**：每個功能至少一條斷言從真實入口（畫面上的按鈕、對外的函式）進去，不能只驗內層純函式。
5. **含 regex 或反斜線的測試碼、補丁，一律用 Write／Edit 工具直接寫檔，不要經過 shell heredoc 或 `node -e`**：`\s` 變 `\\s` 或被吃掉都不報錯、測試照樣綠、但永遠不命中。
6. **打真網路的測試不進 `npm test`**，另開獨立指令；對外部服務的請求頻率照該服務的規矩。
7. **不必每一版都跑全套測試：平常跑受影響的就夠，全面檢測由 Yolin 定期指定。**（Yolin 2026-09-12 對全部專案的指示；2026-09-19 重申：「不用每一次小改動都全測，我會定期進行全面檢測」）這一條是**解除義務，不是設上限**——想多跑、想跑全套，永遠可以，不需要誰同意；本 App 規定每版要跑哪些的，照本 App 的規定。怎麼判定「受影響」由各 App 自己定。沒有放寬的那一條：新斷言仍然必須證明會紅。
   **耗時很久的整套（突變整套、全面檢測）**：等一批交辦事項做完再一起跑、一起看（Yolin 2026-09-19），不必每版跑、也不照固定天數。由 Yolin 指定；Session 不必自己跑（想跑永遠可以）。各 App 在自己的 STATUS 寫明「整套」指什麼、實測要跑多久、以及上限（距上次整套幾版、幾條突變或新斷言從未整套跑過）——上限照本 App 整套的成本訂：要跑幾小時的訂緊一點；只要幾分鐘的可以訂得很寬，或乾脆寫「每版都跑整套、不需要上限」。耗時還沒量過就寫「待量」，不要猜；超過上限時，回報最前面用一行講出來並建議「這一批做完就跑」，沒超過不必每次提。**成本算對地方**：整套是機器在背景跑，花的是時間，不是 token；花 token 的是處理結果的來回——所以要省的是「處理的次數」，結果一次回報、依根因分組。回報寫明是在哪個 commit 上跑的；沒紅的先在最新版複驗再處理。**整套的證據要進 repo**（Yolin 2026-09-23）：每次跑完，把日期、commit、範圍、條數、結果、耗時、沒紅的清單寫進 STATUS 或一個進版控的摘要檔——只存在本機 log 等於沒有紀錄。**完整的 log 寫到 repo 底下、被 `.gitignore` 擋掉的目錄（例如 `.logs/`）**，檔名帶日期與 commit；不要寫在系統暫存目錄或 session 的暫存區——跑好幾個小時的整套，啟動它的 session 可能中途被關掉，暫存目錄會跟著消失。**刪一條突變之前，要能說出這段程式為什麼在任何真實路徑上都走不到**；說不出來，就是測試走錯路，要改的是測試。
8. 隨機或情境敏感的輸出（排程、排菜、抽樣）不得綁死單一結果。需要特定情境才分得出對錯的斷言：優先自己造情境、直接呼叫被測的函式；若用整段產生的結果，先寫一條前置斷言確認情境存在，不成立就紅。**固定 seed 不算釘住情境**（資料或規則一改，同一個 seed 的結果就變）；沒有前置的「至少 1 個」就是假斷言。前置斷言自己也要用突變證明會紅（把情境拿掉，它必須紅）。統計型斷言另照各 App 的做法（多組種子量餘裕）。沒有單元測試層、只有端對端測試的 App，「自己造情境」就用它造得出來的方式（預置儲存狀態、URL 參數）；前置斷言照樣要。
9. **突變的 `expect`**（有這個機制的 App）：`expect` 是用來確認「紅的是指定的那一條」，所以**不要寫會變動的數字或整句訊息**——斷言訊息一改，突變就變成「紅錯地方」。訊息本身沒有穩定的開頭時，不要把 `expect` 寫鬆，而是**在訊息前面加一個固定標籤當錨點**（例：訊息寫成「早餐道數門檻：早餐 N 道…」，`expect` 比「早餐道數門檻：」）。改任何斷言的訊息時，一起搜突變清單裡含舊文字的 `expect`。秒級的突變檢查要同時查「`expect` 在對應測試的原始碼裡找得到」，不必等整套才發現過期；還沒有這個檢查的，列進本 App 的待辦，下次動突變機制時補。
10. **加資料之前，先查畫面上依筆數寫死的上限**（例如選單只列前 N 筆）：新加的資料可能永遠排不進畫面，卻沒有任何測試會紅。有這種上限的，加完要有一條斷言從畫面數得到新資料。

## §6 文件

1. **`docs/STATUS.md` 是接手契約。** 最前面要有「目前進行中／交接」與「等 Yolin 回覆」這兩塊（叫什麼名字、是獨立一節還是小節，照本 App 現有的寫法）；這兩塊過期了就改寫，不要往下追加。只存在對話裡的決定、規則、踩坑，收尾前寫進 STATUS。
2. 規格 `docs/SPEC_<主題>.md`；投票紀錄 `docs/VOTE_<日期>.md`。
3. 文件裡的數字盡量由靜態稽核從程式數出來比對；文件會漂移，而漂移不會讓任何測試變紅。

## §7 本檔怎麼改

2. **只有統籌 Session 改主檔**：第一行版本 +1、日期改當天、§8 加一行。各 App 的副本由該 App 自己的 Session 依統籌者寫的工單更新。副本落後不擋任何工作。

4. Yolin 明訂的直接進；Session 提議的要 Yolin 點頭；會改變四個 App 做法的才開 3 代理投票。
